## 2. Core ideas: models, parameters, training, inference

Before choosing courses or frameworks, it helps to fix a simple mental model of what ML and LLMs are.

### 2.1 Model = function with parameters

In ML, a **model** is a function that maps inputs to outputs:

> \( \hat{y} = f_\theta(x) \)

- **x** – input (numbers that encode data like text, images, audio).  
- **\( \hat{y} \)** – output (prediction or generated content).  
- **f** – architecture (linear model, CNN, Transformer, diffusion model, etc.).  
- **\( \theta \)** – **parameters**: the internal numbers the model learns.

For LLMs, **f** is almost always a Transformer (stacked self‑attention and feed‑forward layers). A “7B” model has about **7 billion parameters** spread across weight matrices and biases.

### 2.2 Parameters, weights, and learned representations

**Parameters** are any values training can change: weights and biases in linear and non‑linear layers. In a simple linear model,

> \( \hat{y} = w x + b \)

the parameters are **w** and **b**. In a neural layer,

> \( \text{output} = \sigma(Wx + b) \)

- **W** – weight matrix.  
- **b** – bias vector.  
- **\( \sigma \)** – activation (fixed function, not a parameter).

In a Transformer‑based LLM, parameters live in:

- Token embeddings and positional/rotary embeddings.  
- Attention projections (Q, K, V, out).  
- Feed‑forward (MLP) layers.  
- Layer norms and output heads.

All of these tensors are stored as **weights** on disk (`.bin`, `.safetensors`, GGUF files, etc.).

### 2.3 Training vs inference

**Training** = changing parameters to reduce a loss:

1. Initialize parameters (randomly or from a pre‑trained checkpoint).  
2. Forward pass: compute predictions.  
3. Compute **loss** (how wrong the predictions are).  
4. Backward pass: compute gradients via backpropagation.  
5. Optimizer update (SGD, Adam, AdamW, etc.).

**Inference** = using frozen parameters to compute outputs:

- Only forward passes; no gradient updates.  
- For LLMs, you apply the model repeatedly to generate tokens one by one.  
- In real systems, most compute and cost are on inference, not training.

This conceptual split—**training changes weights, inference only uses them**—is the foundation of all later details (optimization tricks, quantization, serving frameworks).

## 3. Learning roadmap (2025 overview)

This section summarizes *what* to learn and in *which order*, based on an integrated roadmap. fileciteturn2file0

### 3.1 Phases at a glance

You can think of the journey in five broad phases:

1. **Foundations** – Python, basic math (vectors, dot products, simple probability), basic ML terminology.  
2. **General deep learning** – training simple models, understanding loss, overfitting, and optimization.  
3. **Transformers & LLM intuition** – attention, tokens, context windows, “7B parameters” and what they imply.  
4. **Applied HF & LLMs** – using Hugging Face Hub, `transformers`, `datasets`, Spaces, and inference APIs.  
5. **Specialization & projects** – RAG, fine‑tuning, evaluation, diffusion, agents, or infra (depending on your interests).

Each phase can overlap (you do not need to finish one perfectly before touching the next), but this order avoids many common confusions.

### 3.2 Two paths: coders vs non‑coders

The roadmap distinguishes two main profiles: fileciteturn2file0

- **Path A – Python coders**  
  - Refresh Python → take a code‑first deep learning course (e.g., fast.ai) → learn HF libraries → build and deploy small LLM apps.  
  - Emphasis: writing and reading code, running notebooks, pushing projects to Git or Spaces.

- **Path B – Non‑coders (or “code later”)**  
  - Focus on concepts and tools: take HF Learn courses at a conceptual level, use HuggingChat and Spaces heavily, curate models/datasets via the Hub UI.  
  - Optionally transition into Python later once you have clear reasons to code (e.g., you want specific automations that web UIs cannot do).

Both paths share the same **conceptual core**, but differ in how much code you write.

### 3.3 Projects and capstones

A key principle is to **anchor your learning in real projects**. The roadmap suggests a simple project‑selection loop: fileciteturn2file0

1. Decide your project type (application/system, model analysis, fine‑tuning, or evaluation/leaderboard).  
2. Look for real tasks and baselines (Kaggle, HF Datasets and leaderboards, existing Spaces).  
3. Carve out a small but clear research question (e.g., “Does RAG chunking strategy change accuracy on this corpus?”).  
4. Check feasibility (compute, data, time) and write a one‑page mini‑proposal.

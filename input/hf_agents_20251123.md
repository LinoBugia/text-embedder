## 1. Background and overview

### 1.1 What Hugging Face means by “agent”

In the Hugging Face terminology (AI Agents Course and smolagents docs), an **agent** is an LLM‑powered system that can:

- **Reason** over multiple steps rather than just answering one prompt.
- **Use tools** (APIs, databases, RAG search, code execution, file access, web browsing, etc.).
- **Maintain state or memory** across steps, when needed.
- **Act in an environment**, such as a CLI, web app, IDE, or workflow engine.

By contrast, a “plain” model call is usually **single-shot text in, text out**, without tools or persistent state.

The AI Agents Course stresses that agents are most useful when:

- The task is **multi-step** (search → transform → summarize → act).
- Access to **external data or APIs** is required.
- There are **side effects** (writing files, calling services, updating tickets).
- You need **autonomy** over a sequence of actions, not just an answer.

For simple tasks (short Q&A, basic summarization), the course explicitly suggests using **plain models instead of full agents** to avoid unnecessary complexity.

Key resources:

- AI Agents Course intro:  
  [Welcome to the AI Agents Course](https://huggingface.co/learn/agents-course/unit0/introduction)
- “What are agents?” unit (definition and mental models):  
  [What are Agents?](https://huggingface.co/learn/agents-course/unit1/what-are-agents)

### 1.2 Core components of an agent stack

Across Hugging Face docs, your own specs, and general practice, a typical agent stack consists of:

1. **Reasoning engine**  
   - Usually an LLM or VLM (vision‑language model) accessed via:
     - Hugging Face **Inference Providers** router,
     - **Text Generation Inference (TGI)** or vLLM,
     - Local `transformers` models.

2. **Tools**  
   - Typed functions with clear docstrings and JSON schemas.
   - Examples: RAG retrieval, calculators, HTTP clients, databases, document parsers, MCP servers, Spaces, and other agents.

3. **Planner / controller**  
   - Optional but common: a component that decides which tools to call, in which order, and when to stop.
   - Implemented via:
     - `smolagents` (CodeAgent / ToolCallingAgent),
     - Custom Python logic around Transformers tool use,
     - JS/TS frameworks like Agents.js or Tiny Agents.

4. **Memory and state**  
   - Short‑term: the ongoing conversation history or scratchpad.
   - Long‑term: vector stores, document indexes, or databases (often implemented as **RAG tools**).

5. **Serving and orchestration**  
   - Model serving: Providers router, Inference Endpoints, TGI, vLLM, or local Transformers.
   - Tool hosting: MCP servers, Spaces, HTTP services, local backends.
   - Observability: logs, traces, and metrics for tool calls and model usage.

This KB focuses on how Hugging Face’s libraries and services fill these roles, and how they integrate with your MCP‑centric architecture.

## 3. Models and serving for agents (Inference Providers, HF Inference, local)

### 3.1 From legacy Inference API to Inference Providers

Your migration spec and HF docs note that the old **Serverless Inference API** at:

- `https://api-inference.huggingface.co/models/<model-id>`

has been fully **decommissioned**. It has been replaced by:

- **Inference Providers** and the **router**, exposing an **OpenAI‑compatible API** at:  
  `https://router.huggingface.co/v1`

Key concepts:

- The router fronts multiple providers (Groq, Cerebras, Fireworks, HF Inference, etc.).
- **HF Inference** is the successor of the legacy serverless Inference API, but it is now one provider among many.
- Each model has a **provider‑specific catalog**:
  - Model card “Inference Providers” widget lists which providers host it, for which tasks (chat‑completion, embeddings, image, etc.).
- For agents, this means:
  - Use the router for **chat completion** and tools.
  - Use `InferenceClient` or `@huggingface/inference` for non‑chat tasks (summarization, classification, speech, etc.).

Important changes for agent workloads:

- Code that still calls `api-inference.huggingface.co` will fail and must be migrated.
- Agents should use:
  - An OpenAI‑compatible client with `base_url="https://router.huggingface.co/v1"` and `api_key` set to an HF token with Providers scope, or
  - `huggingface_hub.InferenceClient` (Python) / `@huggingface/inference` (JS) to call Providers / HF Inference.

### 3.2 Token scopes, usage, and cost awareness

For Providers, tokens must be **fine‑grained** with the “Make calls to Inference Providers” permission enabled. This affects agents because:

- Long‑running agents can consume significant tokens via repeated tool calls and planning steps.
- You should monitor usage via:
  - Inference Providers usage breakdown pages on the Hub,
  - The account’s billing dashboard.

HF blog posts and changelog entries highlight:

- Credit‑based pricing across providers.
- Per‑provider cost and latency characteristics.
- Monitoring and debugging tools for Providers usage.

For production agents, you should:

- Implement **limits** (max tokens, recursion depth, tool call budgets).
- Prefer **cheaper/smaller models** for planning or micro‑planning, and reserve larger models for final answers.

### 3.3 Local serving: TGI, vLLM, and Transformers Serve

For agent workloads that need strong control or offline execution, common patterns include:

- **Text Generation Inference (TGI)**:
  - Serves HF models with an OpenAI‑compatible `/v1/chat/completions` Messages API.
  - Supports quantization, batching, and advanced features (e.g., grammar‑guided decoding).
- **vLLM**:
  - `vllm serve <model>` exposes a `/v1` OpenAI‑compatible endpoint.
  - Excellent throughput and support for various quantizations.
- **Transformers Serve** (experimental):
  - `transformers` command to serve models with OpenAI‑compatible APIs.

Agents can then treat these local servers exactly like Providers, by setting `OPENAI_BASE_URL` to the local endpoint.

This is especially useful for:

- **CLI developer agents** (aider, Open Interpreter, OpenHands, smolagent CLI).
- **On‑premise or air‑gapped** agent deployments.
- Situations where you must **pin specific models** (internal fine‑tunes, proprietary checkpoints).

## 4. Python agents with smolagents

### 4.1 Library design goals

From the smolagents docs and HF blog posts, the key design goals are:

- **Simplicity and transparency** – avoid heavy abstractions; keep code close to raw Python.
- **Code‑first agents** – treat the LLM as a code generator and run its code in a controlled interpreter.
- **Tool and backend agnostic** – work with:
  - Local `transformers` models,
  - Hugging Face Inference Providers,
  - OpenAI / Anthropic,
  - Self‑hosted endpoints (TGI, vLLM, etc.).

This matches your two‑speed architecture: smolagents can be used as:

- A **self‑contained agent framework** for small projects.
- A **sub‑executor** inside a larger MCP‑orchestrated system.

### 4.2 CodeAgent

`CodeAgent` is the default “power mode” agent:

- The model writes Python code inside special blocks (e.g., fenced code or explicit “code” markers).
- The agent extracts and executes the code in a sandbox, then returns the result to the model.
- The model can write:
  - Loops and conditionals,
  - Error handling (`try`/`except`),
  - Calls to tools and libraries,
  - Intermediate prints/logging.

Advantages:

- Natural representation for multi‑step reasoning and branching.
- Easy integration with arbitrary Python libraries, subject to sandbox configuration.

Risks and mitigations:

- Untrusted code execution is dangerous by default.
- Docs recommend running in **isolated environments** (Docker, E2B, remote containers) and heavily restricting:
  - Network access,
  - File system paths,
  - Secrets.

Typical pattern:

```python
# pip install smolagents  # see: https://huggingface.co/docs/smolagents/index
from smolagents import CodeAgent, HfApiModel, tool

@tool
def search_docs(query: str) -> str:
    """Searches internal documentation and returns the best matching snippet."""
    # implementation here
    ...

model = HfApiModel(  # or another backend (Inference Providers, local, etc.)
    model="meta-llama/Llama-3.1-8B-Instruct",
)

agent = CodeAgent(
    tools=[search_docs],
    model=model,
    add_base_tools=True,
)

agent.run("Find the deployment steps for our invoice parser and summarize them.")
```

You should replace `HfApiModel` with the appropriate model backend (Inference Providers, local TGI, etc.), as recommended in smolagents and forum threads.

### 4.3 ToolCallingAgent

`ToolCallingAgent` targets models with built‑in **tool use / function calling** capabilities:

- Tools are defined with typed signatures and JSON schemas (similar to OpenAI’s tool format).
- The LLM emits tool calls as JSON; the agent executes them and feeds results back.

This is useful when:

- You want **explicit tool schemas** and don’t need arbitrary code execution.
- The model has strong tool‑use training (e.g., modern open models with function‑calling fine‑tunes).

Tool calling is often sufficient for:

- RAG‑centric agents (call retrieve → call summarize).
- Data pipeline orchestration where tools map neatly to services.

### 4.4 Tools and MCP integration

smolagents supports multiple ways to define and import tools:

- **Local Python tools** via decorators (`@tool`) or helper classes.
- **LangChain tools**, imported and wrapped as smolagents tools.
- **MCP tools** via an internal MCP client:
  - Connect to an MCP server (stdio or HTTP).
  - Import all tools exposed by that server into the agent.
  - Use them as if they were native Python tools.

For your stack, this is particularly important because you already have:

- MCP servers for **RAG** (vector search, rerank) and **Document AI** (OCR, parsing, normalization).
- Possibly other service MCP servers (ticketing, monitoring, search).

With smolagents, an agent can call:

- `docs_rag.search(query="...")` to retrieve documentation snippets.
- `invoice_ocr.extract(path="...")` to process a PDF invoice.
- Any other MCP‑exposed tool, all through a uniform interface.

### 4.5 CLI utilities and local experimentation

smolagents includes CLI helpers such as `smolagent` and `webagent` that let you:

- Run a CodeAgent on the command line with a given model.
- Experiment with web interaction tasks (webagent).

Example:

```bash
# Run a quick coding task (model served via Inference Providers or local)
smolagent "Create a Python script that lists all S3 buckets and prints their sizes."   --model-type InferenceClientModel   --model-id meta-llama/Llama-3.1-8B-Instruct
```

These CLIs are convenient for:

- Trying out new models from the Hub as “coding agents” or “terminal assistants”.
- Testing integration with MCP servers before integrating into bigger systems.

### 4.6 Community patterns and troubleshooting

HF forum threads and posts surface common smolagents topics:

- Using smolagents with **Azure AI / OpenAI endpoints** and managed identities.
- Avoiding `HfApiModel` in favor of **local models** or self‑hosted endpoints.
- Strategies for **deploying smolagents locally** and in production (Docker, Spaces, custom servers).

These discussions reinforce that smolagents is **backend‑agnostic** and that you should pick the serving stack that matches your infra constraints.

## 5. JavaScript / TypeScript agents: Agents.js and Tiny Agents

### 5.1 Agents.js (legacy)

### 6.2 Your two‑speed architecture and MCP

Your architecture combines Hugging Face agents and MCP as follows:

- **Router model (fast path)**  
  - Light model (e.g., small Llama / SmolLM) hosted via Providers or local TGI.  
  - Classifies incoming requests:
    - single‑shot answer,  
    - one or two tool calls,  
    - multi‑step planning needed,  
    - clarification required.

- **Micro‑planner / graph layer (slow path)**  
  - Builds small DAGs of tool calls, with schemas and dependencies.
  - Decides which MCP servers and tools to use (RAG, Document AI, ticketing, monitoring).

- **Execution layer**  
  - Executes DAG nodes using:
    - MCP clients (Python or JS),
    - smolagents for local planning or code execution,
    - Tiny Agents or other agent services as tools.

Hugging Face’s role:

- **Models** – reasoning, planning, and tool‑using LLMs.
- **Serving** – Providers or Inference Endpoints for those models.
- **MCP infrastructure** – HF MCP Server, `huggingface_hub[mcp]`, and Tiny Agents.
- **Libraries** – smolagents for Python agent logic; Agents.js/Tiny Agents for JS; Transformers for low‑level tool use.

This architecture lets you **decouple tool implementations** (as MCP servers) from **agent runtimes** (smolagents, Tiny Agents, IDE hosts).

Agents can orchestrate these tools for workflows like:

## 7. Implementation patterns and tips

### 7.1 Choosing the right level of abstraction

A practical decision tree for Hugging Face–centric agents:

1. **Plain model call** (no agent yet)
   - Use Inference Providers, Inference Endpoints, or local Transformers.
   - Suitable for Q&A, summarization, translation where no tools are needed.

2. **Transformers + tool use**
   - Add simple tools (calculator, search, RAG) via Transformers `chat_extras` to a single LLM.
   - Good for light tool use without a full agent framework.

3. **smolagents (Python)**
   - Use `CodeAgent` when you need heavy Python logic and code execution.
   - Use `ToolCallingAgent` when you want structured tool calls and simpler security.
   - Import MCP tools (RAG, Document AI, etc.) and optionally LangChain tools.

4. **Tiny Agents / JS agents**
   - For front‑end or Node apps that need ready‑made agents.
   - Use Tiny Agents dataset, CLIs, or host your own Tiny Agents definitions.

5. **Full MCP multi‑server architecture**
   - For large systems with many tools and backends (RAG, Document AI, DevOps, analytics).
   - Agents become one “consumer” among many of your MCP servers.

### 7.2 Safety and security

Important considerations:

- **Code execution risk**
  - Restrict CodeAgents to sandboxed environments.
  - Limit outgoing network, file system access, and environment variables.
- **Prompt injection and tool misuse**
  - Use strong system prompts and validated schemas for tool arguments.
  - Implement policies (e.g., tool allowlists per task, explicit confirmation for dangerous tools).
- **Data protection**
  - Ensure that Providers or self‑hosted endpoints respect data residency and privacy requirements.
  - Avoid sending sensitive data to third‑party providers unless contracts and configuration are in place.

### 7.3 Observability and debugging

Given the complexity of agents, you should:

- Trace each **tool call** (input, output, latency, errors).
- Log full **agent runs** (prompt, intermediate decisions, final answer).
- Use observability platforms like **Langfuse** or similar to inspect runs and correlate them with provider usage (credits, latency, failures).

### 7.4 Model and provider choice for agents

Because agents often make **many** calls per user interaction (planning + tools), you should:

- Reserve large, expensive models for high‑impact steps (final answer, complex planning).
- Use smaller, cheaper models for simple tasks (classification, routing, formatting).
- Regularly revisit the **Providers catalog** to select models with favorable cost/quality trade‑offs.

HF’s continuous updates (changelog and blog posts) often introduce new models and provider options that can significantly reduce cost or latency for agents.

## 8. Limitations, caveats, and open questions

1. **API and framework churn**
   - smolagents, Tiny Agents, and MCP tooling are evolving quickly.
   - Some APIs are still labeled “experimental” and may change.
   - Keep a loose coupling between your core business logic and any single agent framework.

2. **Security surface area**
   - Agents increase the attack surface (prompt injection, data exfiltration, tool misuse).
   - Threat modeling and security testing are necessary, especially for CodeAgents with remote code execution.

3. **Provider and model availability**
   - Not all models are available on all Providers for all tasks; provider support can change.
   - You may need **fallback plans**: alternate providers, self‑hosted TGI, or entirely different models.

4. **Complexity vs. benefit**
   - Many tasks can be solved more reliably with deterministic pipelines plus targeted model calls (e.g., RAG + classifier) than with fully autonomous agents.
   - The AI Agents Course itself encourages critical thinking about when agents are truly warranted.

5. **Evaluation and reliability**
   - Agent behavior is harder to evaluate than static model predictions because it includes environment and tool dynamics.
   - Investing in **test harnesses**, scripted scenarios, and regression suites for agents is essential before broad deployment.

These caveats are not unique to Hugging Face but are especially visible when you combine Providers, smolagents, Tiny Agents, and MCP in one system.

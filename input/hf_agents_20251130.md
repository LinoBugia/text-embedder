# Agentic Retrieval-Augmented Generation (Agentic RAG) with Hugging Face

## 1. Background and overview

Agentic Retrieval-Augmented Generation (Agentic RAG) is an evolution of classical Retrieval-Augmented Generation (RAG). In standard RAG, a language model answers a query using information retrieved once from an external knowledge base. In Agentic RAG, **an AI agent controls when and how to retrieve, how to reformulate queries, and how to combine multiple tools and reasoning steps** before producing a final answer.

Key ideas:

- **RAG recap**  
  - Retrieve relevant passages or objects (documents, tables, images, HTML, database rows) from a knowledge base using embeddings, BM25, or hybrid search.  
  - Augment the LLM prompt with these retrieved items.  
  - Generate an answer grounded in this context, with citations or references where possible.

- **Agent recap** (in Hugging Face terminology)  
  - An agent is an LLM-centric system that can use tools, reason over multiple steps, and maintain state.  
  - Tools may include RAG retrieval, web search, code execution, databases, MCP tools, or other agents.

- **Agentic RAG**  
  - Instead of a fixed “retrieve-then-generate” pipeline, retrieval becomes a **tool** inside an agent loop.  
  - The agent decides **what to search**, **when to search**, **how often to re-search**, and **how to mix multiple tools** (RAG, web, analytics, weather, etc.) for a single task.  
  - This enables multi-step patterns such as **query reformulation**, **self-query**, **reflection and critique**, and **multi-agent collaboration**.

From the Hugging Face smolagents example and the Open-Source AI Cookbook recipe, Agentic RAG is framed as an “agent armed with a retriever tool” that can:  
1. Formulate better search queries than the raw user question.  
2. Critique and re-run retrieval when initial results are poor.  
3. Combine advanced RAG patterns (HyDE, self-query, reranking) under the control of an agent loop rather than hard-coded pipeline logic.

Recent academic work, such as the 2025 survey “Agentic Retrieval-Augmented Generation: A Survey on Agentic RAG”, further emphasizes that Agentic RAG integrates **planning, tool use, reflection, and multi-agent collaboration** into the RAG paradigm, enabling richer workflows across domains like healthcare, finance, and education.

### 2.1 What “Agentic RAG” means in smolagents docs

The smolagents documentation has a dedicated **Agentic RAG** example that builds an agent able to answer questions about the Hugging Face Transformers library based on a documentation dataset. The main steps are:

1. **Knowledge base construction**  
   - Load a dataset containing documentation pages as Markdown (for example, a dataset of Hugging Face docs).  
   - Filter down to a subset (e.g. only `transformers` docs).  
   - Convert rows into `Document` objects with helpful metadata like `source` identifiers.  
   - Use a `RecursiveCharacterTextSplitter` or similar scheme to split long texts into overlapping chunks.

2. **Retrieval setup**  
   - Build retrievers using utilities such as BM25 and dense embeddings (often via LangChain or direct integration with TEI or sentence-transformers).  
   - Store chunks in a vector store; optionally combine dense and sparse retrieval.

3. **Agent definition**  
   - Implement a **retriever tool** that accepts a query string and returns the most relevant documentation snippets.  
   - Wrap this tool and a language model backend into a smolagents agent (e.g. a `CodeAgent` or `ToolCallingAgent`).  
   - Configure the LLM backend via Hugging Face Inference Providers, Inference Endpoints, or another OpenAI-compatible endpoint.

4. **Agentic control**  
   - The agent **does not just call retrieval once**. Instead, it:  
     - Generates an intermediate “reference” sentence or hypothetical answer (HyDE-like behavior) and embeds that for semantic search.  
     - Inspects the retrieved snippets, and if they seem off-topic or incomplete, emits another retrieval call with a refined query (self-query).  
   - This loop turns advanced RAG techniques into **emergent behavior** of the agent rather than a fixed pipeline of steps.

The example shows how a relatively simple design (retrieval as a tool, basic agent loop) can recover and unify techniques like HyDE and self-query in a single system.

## 3. Design patterns for Agentic RAG

### 3.1 From pipeline RAG to agentic RAG

A classic RAG pipeline has the shape:

1. Receive user query.  
2. Retrieve top-k chunks.  
3. Concatenate context and question.  
4. Call LLM once.  
5. Return answer.

Agentic RAG refactors this into an **agent loop** with tools:

1. Receive user query.  
2. Agent decides whether it can answer directly from parametric knowledge or needs external information.  
3. If needed, agent calls a **retriever tool** with a carefully crafted query:  
   - Possibly different from the original user question.  
   - Possibly generated using HyDE or self-query patterns.  
4. Agent inspects retrieved documents and optionally:  
   - Calls the retriever again with a refined query.  
   - Switches to another tool (e.g. web search, DB query, code execution).  
5. Agent assembles final context and synthesizes an answer.  
6. In more advanced designs, another agent verifies or supplements this answer.

Conceptually, **retrieval becomes a controllable decision** rather than a fixed step. This provides more robustness against poor retrieval, noisy corpora, and complex tasks that require multiple knowledge sources.

### 3.2 Query reformulation and self-query

The smolagents and Cookbook resources emphasize two key techniques:

- **Query reformulation**  
  - The agent rewrites the user’s question into a more retrieval-friendly statement.  
  - This can add missing context, expand abbreviations, or convert a question into an answer-like statement (HyDE).  
  - Example transformations:  
    - “How do I load a pretrained BERT model?” → “Loading a pretrained BERT model with AutoModel and AutoTokenizer.”  
    - “What’s the config option for 8-bit quantization?” → “Description of configuration options enabling 8-bit quantization.”

- **Self-query / iterative retrieval**  
  - The agent uses intermediate results (draft answers, summaries, or extracted entities) to refine new retrieval queries.  
  - It can explicitly reason: “The retrieved docs do not mention X; I should search for X explicitly.”  
  - It can adapt retrieval parameters (e.g. `top_k`, filters, index choice) across iterations.

Agentic RAG combines these techniques inside the agent’s reasoning process rather than needing separate orchestrators or pipelines.

### 3.3 Tool design for Agentic RAG

In a Hugging Face-based stack, basic tools for Agentic RAG usually include:

- **Retriever tools**  
  - A generic `search_docs(query: str) -> list[Document]` tool that hits a vector DB with TEI embeddings.  
  - Specialized retrievers per index: `search_api_docs`, `search_incident_logs`, `search_kb_articles`, etc.  
  - Tools for reranking (e.g. calling a TEI reranker or cross-encoder).

- **Auxiliary knowledge tools**  
  - Web search or browser tools.  
  - Domain-specific APIs (e.g. ticketing systems, monitoring dashboards, BI/analytics).  
  - Tools for HTML or PDF extraction, visual document retrieval, or tabular queries.

- **Meta-tools**  
  - Tools to summarize or cluster retrieved documents.  
  - Tools to transform documents into structured outputs (JSON, tables).  
  - Tools for evaluation or sanity checks (e.g. verifying that each claim is supported by context).

Good tool design for Agentic RAG includes:

- Clear, concise docstrings and argument types.  
- Structured responses that are easy for the agent to parse (JSON-like outputs).  
- Strong input validation and safe defaults (e.g. maximum `top_k`).

### 3.4 Single-agent vs multi-agent RAG

Agentic RAG can be implemented with:

- **A single agent** with several tools:  
  - Simpler to implement and deploy.  
  - Suitable when the domain is narrow or the tool set is small.  
  - The agent internally handles retrieval, reasoning, and answer generation.

- **Multiple cooperating agents**:  
  - Each agent has its own tools and specialization.  
  - The Multi-agent RAG System Cookbook shows patterns like a retriever agent plus synthesis agent plus coordinator.  
  - Multi-agent setups are useful when:  
    - Different indices require different retrieval logic.  
    - You want explicit separation of concerns (retrieval vs reasoning vs verification).  
    - You need robust fallback paths and multiple perspectives on complex tasks.

Your own architecture (router, micro-planner, tool graph executor) fits naturally into this multi-agent view: the router decides whether to trigger a simple agentic RAG flow or a more complex multi-agent DAG involving multiple RAG and non-RAG tools.

### 3.5 Multimodal and HTML Agentic RAG

Agentic RAG is not limited to text:

- **HTML RAG**  
  - Agents use HTML-aware retrievers and parsers to extract relevant parts of web pages or documentation sites.  
  - Retrieval can operate on HTML nodes, sections, or link graphs, not just plain text chunks.  
  - Agents learn to combine HTML metadata (titles, headings, links) with textual content.

- **Multimodal RAG**  
  - Vision-language models (VLMs) and visual retrievers (e.g. ColPali) allow retrieval over images or pages.  
  - Agentic frameworks can route between text-based and image-based retrievers depending on the query.  
  - For example, an agent might:  
    - Use a visual retriever on PDF pages to find relevant tables.  
    - Then pass the cropped image to a VLM to read the table.  
    - Finally combine this with text-based RAG from associated docs.

The “HTML and multimodal Agentic RAG” resources highlight that **agentic decision-making over multiple modalities** is often more important than any single retrieval technique.

## 4. Implementation with Hugging Face components

### 4.1 Agentic RAG with smolagents

In Python, smolagents provides a lightweight framework for Agentic RAG. A typical pattern is:

1. Implement a retriever tool:

```python
from smolagents import tool

@tool
def search_kb(query: str, top_k: int = 5) -> str:
    """Retrieve relevant passages from the internal knowledge base.
    Returns a JSON string with a list of {id, title, text, url}.
    """
    # Call your vector DB + reranker here.
    # Return serialized results that the agent can parse.
    ...
```

2. Configure a model backend (Inference Providers, local TGI, vLLM, etc.) and create a `ToolCallingAgent` or `CodeAgent`:

```python
from smolagents import ToolCallingAgent, HfInferenceModel

model = HfInferenceModel(  # or another backend class
    model_id="meta-llama/Meta-Llama-3-8B-Instruct",
)

agent = ToolCallingAgent(
    tools=[search_kb],
    model=model,
    system_prompt=(
        "You are an agentic RAG assistant. Use the search_kb tool to "
        "retrieve information when needed. Reformulate queries if "
        "initial results look irrelevant or incomplete."
    ),
)
```

3. Run the agent with user queries:

```python
result = agent.run("How do I fine-tune a Transformers model with PEFT?")
```

Inside the agent, the model decides when to call `search_kb`, how to phrase the query, and whether to call it multiple times before answering. You can extend this pattern with more tools (web search, HTML parsers, code execution, monitoring APIs) to implement fully agentic workflows.

### 4.2 Agentic RAG with Transformers tool use

If you prefer not to use a separate agent framework, you can use **Transformers chat extras** and “tool use” directly:

- Define tools with JSON schemas and function signatures.  
- Pass them to a chat-capable model that supports function calling.  
- Implement a loop where the model:  
  - Emits a tool call (e.g. the RAG retriever).  
  - Receives the tool result in a follow-up message.  
  - Decides whether to call another tool or produce a final answer.

This approach is lower-level than smolagents but can be useful for fully custom orchestration, or when integrating with an existing framework or router.

### 4.3 Multi-agent RAG with smolagents and MCP

For multi-agent Agentic RAG systems, you can:

- Create multiple smolagents agents, each with its own tool set.  
- Use one agent as a **coordinator** and treat other agents as tools (for example, a retriever agent that returns summarized context).  
- Expose RAG services, Document AI, and analytics via **MCP servers** and import them as tools into agents.

A typical pattern in an MCP-centric architecture:

- One MCP server exposes:  
  - `rag.search_docs` for vector retrieval.  
  - `rag.rerank` for reranking.  
  - `rag.semantic_cache` for caching.  

- Another MCP server exposes Document AI operations (OCR, structuring, validation).  

- Agents (Python smolagents or JS Tiny Agents) connect to these servers via MCP clients and use the tools as part of their Agentic RAG workflows.

This decouples tool implementation from agent runtimes, making it easier to switch between backends and languages while reusing the same RAG and Document AI stacks.

Agentic RAG stacks on Hugging Face commonly mix:

- **Hosted components**  
  - Hugging Face Inference Providers or Inference Endpoints for LLMs and embeddings.

For local or on-premise scenarios (including AI PCs), you can run:

- A local LLM backend (llama.cpp, Ollama, vLLM, TGI).  
- A local TEI-like embedding server.  
- Local vector DB and Document AI backends.  
- Agent logic (smolagents or other) in a local service or CLI.

Because smolagents and Tiny Agents are backend-agnostic, the same Agentic RAG logic can often be reused while swapping endpoints and configuration.

  - Correctness.  
  - Groundedness (is the answer supported by retrieved context?).

- More precise retrieval queries.  
- Multi-step reasoning across different documentation sections.  
- Handling of ambiguous or underspecified queries.

### 5.2 Instrumentation and logs

Agentic RAG systems are inherently more complex than single-shot RAG, so **observability is crucial**:

- Log each **tool call** (arguments, outputs, latency, errors).  
- Track **agent steps**, including internal reasoning traces when possible (subject to privacy and security).  
- Record which documents were retrieved and which were actually cited in the final answer.  
- Correlate user-facing metrics (latency, user feedback, task completion) with internal metrics (number of tool calls, retrieval quality).

This data is essential for:

- Debugging retrieval failures and hallucinations.  
- Optimizing cost and latency by adjusting agent policies.  
- Measuring the impact of improvements to retrievers, embeddings, index structure, or prompts.

### 5.3 Specialized evaluation tools

Beyond LLM-judge metrics, you can use specialized evaluation frameworks:

- RAG-specific evaluation frameworks (such as RAGAS, DeepEval, or custom HF Spaces) for measuring answer quality and groundedness.  
- Task-specific benchmarks (e.g. QA, troubleshooting, coding tasks) for regression testing.  
- Multi-agent evaluation setups where different agents cross-check each other’s answers, or where a dedicated evaluation agent assigns scores.

For Agentic RAG, it is particularly important to test:

- **Failure modes**: when agents overuse tools, loop unnecessarily, or make poor tool choices.  
- **Step-level robustness**: whether individual steps are stable under small perturbations in prompts or data.  
- **Cross-agent consistency**: whether multiple agents agree on answers within expected variance.

## 6. Limitations, caveats, and open questions

### 6.1 Accumulated risk of hallucinations

Agentic RAG often calls the LLM many times per user request: for planning, retrieval, synthesis, verification, and sometimes even evaluation. Each step has a non-zero probability of hallucination.

- If each call has, for example, a 10% chance of introducing an error, a long 8-step agentic workflow can have a much higher probability of containing at least one incorrect statement.  
- Blogs on “hallucination-free RAG” highlight that agentic workflows **amplify** this risk unless mitigation steps are in place.

Mitigations include:

- Strict instructions and answer templates.  
- Evidence-focused prompting (e.g. “quote exact spans from documents”).  
- Post-hoc verification steps that check claims against retrieved context.  
- Conservative fallback behavior when context is missing or contradictory.

### 6.2 Cost and latency

Agentic RAG systems can be expensive and slow if left unconstrained:

- Multiple retrieval iterations, complex planning, and many verification steps increase token usage and wall-clock time.  
- Multi-agent systems introduce additional overhead from inter-agent communication.

To control this, you should:

- Set **budgets**: maximum number of tool calls, maximum planning depth, token limits per step.  
- Use **smaller models** for planning and micro-decisions, reserving larger models for final answers.  
- Implement **adaptive policies** that adjust the amount of reasoning based on query complexity or user tier.

Research on SLA-managed multi-agent RAG systems explores dynamic orchestration strategies that tune the number of agents and steps based on latency and quality targets.

### 6.3 Complexity and debugging

Agentic RAG systems are harder to reason about and debug than simple pipelines:

- Behavior emerges from the interaction of prompts, tools, data, and model weights.  
- A bug can originate in retrievers, index configuration, tool schemas, or model prompts.

To mitigate this:

- Keep the **initial design minimal** and only introduce additional agents or tools when clearly necessary.  
- Add **strong logging and tracing** from the beginning.  
- Maintain simple, deterministic tests for each tool and for core workflows.  
- Consider using separate “debug” and “production” configurations, with more verbose reasoning in debug mode.

### 6.4 Safety and tool misuse

Agentic RAG systems are powerful; they can modify files, call APIs, and act in external environments. This raises safety concerns:

- Prompt injection and tool misuse can cause agents to exfiltrate data, make unsafe changes, or interpret malicious documents as instructions.  
- Multi-agent setups can inadvertently amplify the effects of compromised tools or agents.

Mitigation strategies include:

- Hardened tool schemas and input validation.  
- Strict allowlists and policy checks for high-risk tools.  
- Dedicated **security agents** or scanners that inspect tool schemas and prompts for vulnerabilities.  
- Regular audits and reviews of MCP servers and external tool providers.

### 6.5 Research directions

Open questions for Agentic RAG include:

- How to automatically choose between standard RAG, Agentic RAG, and multi-agent RAG for a given query.  
- How to best combine Agentic RAG with structured data access (SQL, knowledge graphs, OLAP).  
- How to design benchmarks that stress real-world workflows rather than only static QA.  
- How to integrate program synthesis, planning, and verification agents in a way that remains interpretable and debuggable.  
- How to ensure alignment and safety when agents can autonomously generate tool workflows and modify their own prompts or code.

## 7. Practical checklists

### 7.1 When to use Agentic RAG

Use Agentic RAG when:

- Queries regularly require **multi-step retrieval** or data from multiple sources.  
- Vanilla RAG often fails due to ambiguous or underspecified queries.  
- You need to integrate RAG with other tools (web, analytics, ticketing, monitoring).  
- You want more robust handling of complex, long-running tasks.

Stick to standard RAG (or even plain LLM calls) when:

- Questions are simple, narrow, and well-covered by a single index.  
- Latency and cost constraints are very strict.  
- Tool ecosystems are minimal.

### 7.2 Minimal Agentic RAG blueprint

A minimal but robust Agentic RAG system might look like this:

- **Tools**
  - `search_kb` (vector DB with TEI embeddings).  
  - `web_search` for external data (optional).  
  - `summarize_docs` for condensing large contexts.

- **Agent**
  - A smolagents ToolCallingAgent with a strong instruction to:  
    - Reformulate queries for retrieval.  
    - Call `search_kb` at least once for knowledge-intensive questions.  
    - Re-run retrieval if initial documents do not address the question.  
    - Keep final answers grounded in cited documents.

- **Infrastructure**
  - TEI or equivalent embedding server.  
  - Vector DB and metadata-aware indexing.  
  - LLM backend via Inference Providers, TGI, vLLM, or local engines.

- **Evaluation**
  - Small test suite of real user questions.  
  - LLM-judge evaluation for correctness and groundedness.  
  - Basic logging of tool calls and retrieved documents.

From this base, you can progressively add multi-agent roles, more tools, multimodal capabilities, and richer evaluation strategies.

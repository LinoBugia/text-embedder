# Kaggle for Deep Learning and LLM Workflows

## 1. Background and overview

Kaggle is a hosted environment for data science and machine learning that combines:

- Public and private datasets and models.
- Jupyter-based Notebooks with free CPU, GPU, and TPU runtimes.
- Competitions, code examples, and community discussions.

For deep learning and large language models (LLMs), Kaggle matters because it offers:

- **Free access to accelerators**: CPU-only, single GPU (P100), dual GPU (T4x2), and TPU v3–8 VM runtimes, with weekly hour quotas.
- **Integrated storage**: Input datasets mounted read-only, `/kaggle/working` for writeable outputs and checkpoints, and `/kaggle/temp` for ephemeral files.
- **Reproducible environments**: Pinned package environments, reproducible notebook versions, and scheduled executions.

As of 2024–2025, a typical Kaggle notebook runtime looks like:

- **Default (CPU)**: 2× Intel Xeon CPUs, 32 GB RAM.
- **GPU P100**: 1× NVIDIA Tesla P100 16 GB VRAM, 32 GB RAM.
- **GPU T4x2**: 2× NVIDIA T4 GPUs (16 GB each), 32 GB RAM.
- **TPU VM v3–8**: 8 TPU v3 cores with 128 GB HBM, accessed via the TPU VM runtime.

GPU environments are usually capped at around **30 hours per week**, TPUs at about **20 hours per week**, and sessions at around **12 hours per notebook run**, depending on Kaggle’s current policy. Always check Kaggle’s official documentation and product updates for the latest numbers.

Kaggle is best suited for:

- Prototyping and small-to-medium experiments.
- Running lighter LLM fine-tuning (e.g., LoRA/QLoRA on 7B–14B models).
- Running local-weights inference and experimentation with model runtimes (Transformers, Diffusers, llama.cpp, vLLM via CPU/GPU, or PyTorch/XLA via TPU).

For sustained large-scale training or production inference, you will eventually need dedicated cloud resources (e.g., Google Cloud, RunPod, Hugging Face Jobs, or on-prem hardware), but Kaggle is an effective free on-ramp.

## 2. Hardware, quotas, and environment basics

### 2.1 Hardware profiles

Kaggle notebooks expose the accelerator type via the Notebook **Settings → Accelerator** menu. The main options are:

- **None (CPU)**: General-purpose work, feature engineering, light inference.
- **GPU P100**: Good single-GPU baseline for CV, tabular DL, or moderate LLM tasks.
- **GPU T4x2**:
  - 2× NVIDIA T4 (16 GB each), often used for:
    - Multi-GPU data parallel training.
    - Large-context diffusion or image models.
    - Large LLM inference with tensor-split or pipeline parallelism.
- **TPU VM v3–8**:
  - 8 TPU v3 cores.
  - Accessed via TPU VM semantics: the notebook runs directly on the TPU VM; `/kaggle/input` and `/kaggle/working` behave like normal Linux paths.
  - Used via TensorFlow, JAX, or PyTorch/XLA.

While the exact quotas can evolve, typical limits are:

- **Per-week accelerator hours** (approximate):
  - 30 hours for GPUs (shared across P100 and T4x2).
  - 20 hours for TPU v3–8.
- **Per-session runtime limit**:
  - ≈12 hours (CPU/GPU).
  - ≈9–12 hours (TPU), depending on configuration and current policies.

These quotas reset weekly and may be throttled by account-specific factors (e.g., phone verification). If accelerators are greyed out in the Notebook settings, you may need to:

- Verify your phone number.
- Ensure you have remaining weekly quota.
- Use the right sidebar “Session options” panel in the new UI to change the accelerator.
- Restart the session after changing accelerator type.

### 2.2 Filesystem layout and persistence

The key paths in Kaggle notebooks are:

- `/kaggle/input/`: Read-only datasets (and sometimes models) attached to the notebook.
- `/kaggle/working/`: Writeable, persistent between runs for the same notebook; max size is around 20 GB with a file-count limit.
- `/kaggle/temp/` or `/kaggle/tmp/`: Temporary space that may not persist and can be safely used for caches.

Good practices:

- Save **checkpoints**, **logs**, and important **artifacts** to `/kaggle/working`.
- Keep only a small number of large checkpoints (e.g., rotate 2–3 files) to avoid hitting disk limits.
- Use `/kaggle/temp` for temporary artifacts (e.g., caches, intermediate images) that can be recomputed.

### 2.3 Environment and packages

Kaggle provides a base conda environment with common data science and deep learning packages. To customize:

- Use `pip install`/`pip install -U` in the first notebook cell for additional packages.
- Avoid mixing incompatible CUDA/TPU packages in the same environment (e.g., don’t install GPU-only extensions like FlashAttention when using TPU runtimes).
- For PyTorch/XLA or specialized runtimes, pin versions explicitly (e.g., `torch==2.8.0`, `torch_xla[tpu]==2.8.0`) and install from the official wheels index.

Because environment changes may be lost when the session ends, it is common to:

- Put installation commands in the first cell.
- Optionally create a custom Kaggle “environment timestamp” (using Kaggle’s environment pinning) to keep system packages stable.

## 3. Using GPUs on Kaggle (P100 and T4x2)

### 3.1 General GPU workflow

With a GPU accelerator enabled:

1. **Confirm GPU presence**:

   ```python
   import torch
   print(torch.cuda.is_available(), torch.cuda.device_count())
   print(torch.cuda.get_device_name(0))
   ```

2. **Move models and tensors** to GPU:

   ```python
   device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
   model.to(device)
   for batch in dataloader:
       x, y = batch
       x, y = x.to(device), y.to(device)
       ...
   ```

3. **Use mixed precision** when appropriate:

   - For T4 or P100 GPUs, use `torch.float16` (FP16) in AMP.
   - Use `torch.cuda.amp.autocast()` and `GradScaler` to speed up training and reduce memory.

#### Important: T4 does not support CUDA bfloat16

On T4 GPUs, **CUDA bfloat16 is not supported**. If you attempt to use `torch.bfloat16` on CUDA, it may fall back to CPU or error out. For T4, choose:

- FP16 (`torch.float16`) for performance and memory savings.
- FP32 (`torch.float32`) for maximum numerical stability when memory allows.

This matters especially for:

- Diffusers pipelines.
- Custom kernels.
- LLM inference frameworks that default to bfloat16 on newer GPUs.

### 3.2 Multi-GPU (T4x2) patterns

The T4x2 runtime gives you 2 GPUs with 16 GB each. Common patterns:

1. **Simple data parallelism**

   ```python
   import torch
   if torch.cuda.device_count() > 1:
       print("Using", torch.cuda.device_count(), "GPUs")
       model = torch.nn.DataParallel(model)
   model.to("cuda")
   ```

   This is acceptable for smaller models and quick experiments, though fully sharded approaches (FSDP, DeepSpeed, Accelerate) can be more efficient.

2. **Accelerate with `device_map` and `max_memory`**

   For libraries like Hugging Face Transformers and Diffusers, you can:

   - Use `device_map="auto"` or `"balanced_low_0"` to shard layers across GPUs.
   - Specify per-device VRAM budgets via `max_memory` to keep usage below roughly 14–15 GB per T4.

   Example pattern for a diffusion or LLM pipeline:

   ```python
   from transformers import AutoModelForCausalLM
   import torch

   max_memory = {
       0: "14GiB",
       1: "14GiB",
       "cpu": "30GiB",
   }

   model = AutoModelForCausalLM.from_pretrained(
       "your/model-id",
       torch_dtype=torch.float16,
       device_map="balanced_low_0",
       max_memory=max_memory,
   )
   ```

   Avoid mixing manual `.to("cuda")` calls after using `device_map`; let Accelerate manage placements.

3. **Multi-GPU with llama.cpp or similar runtimes**

   If you use llama.cpp-based runtimes with GGUF models:

   - Use `--split-mode layer` and `--tensor-split 50,50` (or similar) to spread layers across 2 GPUs.
   - Keep enough headroom for KV cache (context length × batch size × model size).

### 3.3 Example: QwenImageEditPlus with GGUF on T4x2

When running image-editing diffusion pipelines like QwenImageEditPlus with Diffusers and GGUF quantization on 2×T4:

- Use **FP16** (`torch.float16`) as the compute dtype; avoid BF16 on CUDA T4.
- Load the GGUF transformer via `from_single_file` with a `GGUFQuantizationConfig` set to FP16 compute.
- Use `device_map="balanced_low_0"` (or `"auto"`) to let Accelerate place submodules across both GPUs.
- Enable sequential CPU offload and attention slicing to reduce memory spikes.
- Ensure that the **random number generator (RNG)** lives on the pipeline’s execution device:

  ```python
  exec_device = getattr(pipe, "_execution_device", getattr(pipe, "device", torch.device("cuda:0")))
  generator = torch.Generator(device=exec_device).manual_seed(1234)
  ```

This avoids “indices should be on the same device” errors and mismatched device issues where masks or indices end up on CPU while tensors are on GPU.

### 3.4 Common GPU pitfalls on Kaggle

- **Out-of-memory (OOM)**:
  - Reduce batch size.
  - Use FP16/AMP.
  - Lower resolution or context length.
  - Avoid large `num_workers` in DataLoader; start with `num_workers=0` and increase carefully.
- **Device mismatch errors**:
  - Ensure all tensors used in indexing / masking operations are on the same device.
  - Avoid mixing manual `.to()` calls with `device_map` or offload utilities.
- **Long first step**:
  - PyTorch, XLA, and some LLM runtimes compile or warm up on the first batch; expect a slower first iteration.

## 4. Using TPUs on Kaggle with PyTorch/XLA

### 4.1 TPU VM basics

Kaggle uses **TPU VMs**: your notebook runs directly on the VM that has TPU v3–8 attached. This simplifies data access (no GCS mount needed) but changes some environment assumptions compared to legacy XRT-based TPUs.

To use TPUs:

1. Set **Notebook Settings → Accelerator → TPU** (TPU v3–8 VM).
2. Install matching PyTorch and PyTorch/XLA wheels:

   ```bash
   pip -q install "torch==2.8.0" "torch_xla[tpu]==2.8.0" -f      https://storage.googleapis.com/libtpu-releases/index.html
   ```

3. (Optionally) set the runtime environment:

   ```bash
   export PJRT_DEVICE=TPU
   ```

4. Verify TPU visibility:

   ```python
   import torch_xla as xla
   import torch_xla.core.xla_model as xm

   print("XLA devices:", xm.get_xla_supported_devices("TPU"))
   ```

   Expect 8 devices (`xla:0`…`xla:7`) for a v3–8 instance.

### 4.2 Single-core vs multi-core training

PyTorch/XLA is designed for multi-core TPU training, usually via 8 processes (one per core). In notebooks, the recommended approach is:

- Use **Accelerate’s `notebook_launcher`** (or `torch_xla.distributed.xla_multiprocessing` directly) to spawn workers.
- Build or pass your model, dataset, and collator into a `main()` function launched by `notebook_launcher`.

Example with Hugging Face `Trainer` on TPU:

```python
from transformers import Trainer, TrainingArguments
from accelerate import notebook_launcher

def training_loop(model, train_dataset, data_collator):
    args = TrainingArguments(
        output_dir="output",
        per_device_train_batch_size=1,
        num_train_epochs=1,
        bf16=True, fp16=False,
        logging_steps=10,
        report_to="tensorboard",
        tpu_num_cores=8,            # informational; launcher handles actual setup
        dataloader_num_workers=0,
    )
    trainer = Trainer(
        model=model,
        args=args,
        train_dataset=train_dataset,
        data_collator=data_collator,
    )
    print("Starting training on TPU")
    trainer.train()

notebook_launcher(
    training_loop,
    args=(model, train_dataset, data_collator),
    num_processes=8,
)
```

Key points:

- `tpu_num_cores` in `TrainingArguments` does **not** start TPU workers; the launcher does.
- Build the `Trainer` **inside** the launched function or pass pre-built objects as arguments to avoid pickling issues.
- Keep `bf16=True` where supported; TPUs are optimized for bfloat16. Do not use `fp16=True` on TPUs.

### 4.3 Common TPU trouble patterns and fixes

Frequent issues when using Kaggle TPUs with PyTorch/XLA:

1. **Import or installation mismatch**:

   - Symptom: `import torch_xla` fails or no TPU devices show up.
   - Fix: Ensure `torch` and `torch_xla[tpu]` versions match and come from the official libtpu wheel index.

2. **Legacy XRT vs PJRT confusion**:

   - Kaggle TPUs use the **PJRT** runtime by default.
   - Do not rely on old `XRT_TPU_CONFIG` recipes; instead, set `PJRT_DEVICE=TPU` when needed and follow recent PyTorch/XLA docs.

3. **Multi-core crashes or hangs**:

   - Start with `debug_single_process=True` or single-core prototypes.
   - Ensure no XLA interaction happens at module import time; wrap XLA device usage inside functions called by spawned processes.
   - Avoid heavy logging in inner loops; use periodic prints.

4. **Notebook appears “stuck”**:

   - The first few steps may trigger compilation, which can take minutes.
   - Avoid dynamic shapes and frequent graph changes; keep batch sizes, sequence lengths, and model structure stable.

5. **Checkpoint saving issues**:

   - Prefer rank-0 saving via `xm.save` outside tight loops.
   - Move tensors to CPU before `torch.save` if needed to avoid hangs.

## 5. Kernel crashes and resource limits on Kaggle

### 5.1 Understanding `DeadKernelError`

A `DeadKernelError` in Kaggle means the underlying Jupyter kernel process exited unexpectedly. Common root causes:

- GPU or CPU **out-of-memory (OOM)**.
- Long-running cells that hit Executor timeouts.
- Hitting platform runtime limits (e.g., 12-hour cap).
- Disk quota exceeded on `/kaggle/working`.
- Native crashes in libraries (segfaults in CUDA or C++ extensions).

Because Kaggle “Run All” and offline execution use nbclient under the hood, a non-responsive or crashed kernel surfaces as `DeadKernelError`.

### 5.2 OOM and DataLoader-related issues

OOM is the most frequent cause. For PyTorch training loops:

- Start with conservative `DataLoader` settings:

  ```python
  from torch.utils.data import DataLoader

  train_loader = DataLoader(
      dataset,
      batch_size=32,
      shuffle=True,
      num_workers=0,             # increase later if stable
      persistent_workers=False,
      prefetch_factor=2,
      pin_memory=False,
  )
  ```

- Avoid doing GPU work inside `Dataset.__getitem__`; keep that logic on CPU and move tensors to GPU in the training loop.
- Enable AMP and, if necessary, activation checkpointing to reduce memory usage.
- Monitor memory periodically:

  ```python
  import torch, gc

  def log_memory(step):
      torch.cuda.empty_cache()
      gc.collect()
      alloc = torch.cuda.memory_allocated() / 2**20
      reserved = torch.cuda.memory_reserved() / 2**20
      print(f"[step {step}] alloc={alloc:.1f} MiB, reserved={reserved:.1f} MiB")
  ```

### 5.3 Timeouts, runtime limits, and disk quotas

- **Timeouts**:
  - nbclient enforces per-cell timeouts and iopub (output) timeouts.
  - Long-running cells with no output can be killed even if the process is still working.
  - Workaround: print periodic “heartbeat” messages or use progress bars (e.g., `tqdm`) to generate output.

- **Runtime limits**:
  - Kaggle enforces maximum session durations; long training can be interrupted even if code is correct.
  - Mitigation: design training to checkpoint periodically and support resume.

- **Disk quotas**:
  - `/kaggle/working` has size and file-count limits. Exceeding them can cause I/O failures and, in some cases, kernel crashes.
  - Mitigation: limit the number of checkpoints and logs; clean up intermediate files; use `/kaggle/temp` for ephemeral artifacts.

### 5.4 Triage checklist

When you see `DeadKernelError` on Kaggle:

1. Check GPU and CPU memory usage (`!nvidia-smi`, `!free -h`) during training.
2. Reduce batch size and DataLoader complexity (`num_workers`, `prefetch_factor`).
3. Add periodic logging inside long loops.
4. Monitor disk usage in `/kaggle/working`.
5. If problems persist, pin or change versions of heavy libraries (PyTorch, Transformers, Diffusers) and re-run with a minimal reproducer.

## 6. Kaggle for LLM fine-tuning and inference

### 6.1 What fits in Kaggle’s free hardware

With Kaggle’s free hardware, you can realistically:

- **Fine-tune smaller LLMs (≤14B parameters)** with LoRA/QLoRA on GPUs:
  - 7B models at 4-bit or 8-bit quantization are comfortable on 16 GB T4 or P100.
  - 13–14B models can fit with aggressive quantization and careful RAM/VRAM management.
- **Train or fine-tune smaller encoder models** (e.g., sentence encoders, small Transformers) on GPUs or TPUs.
- **Run inference** with larger models using quantization (GGUF, AWQ, GPTQ), especially with llama.cpp or vLLM on T4 GPUs.

Examples of realistic workloads:

- Fine-tuning Qwen 2.5 or Gemma-like 7B models with LoRA for domain-specific chat or coding.
- Training a RoBERTa- or DistilBERT-sized model from scratch on a moderate dataset.
- Running local inference of 7B/8B models at reasonable speed; 13B+ at lower throughput.

### 6.2 Typical fine-tuning pattern on GPU

A Kaggle GPU fine-tuning script often includes:

- Loading a pre-trained model and tokenizer from Hugging Face Hub.
- Applying parameter-efficient fine-tuning (PEFT) such as LoRA.
- Using a Trainer or Accelerate-powered training loop with careful batch sizes and gradient accumulation.

High-level example:

```python
from transformers import AutoModelForCausalLM, AutoTokenizer
from peft import LoraConfig, get_peft_model
from datasets import load_dataset

model_id = "Qwen/Qwen2.5-7B-Instruct"
tokenizer = AutoTokenizer.from_pretrained(model_id, use_fast=True)

model = AutoModelForCausalLM.from_pretrained(
    model_id,
    torch_dtype=torch.float16,
    device_map="auto",
)

lora_config = LoraConfig(
    r=16,
    lora_alpha=32,
    target_modules=["q_proj", "v_proj"],
    lora_dropout=0.05,
    bias="none",
    task_type="CAUSAL_LM",
)
model = get_peft_model(model, lora_config)

dataset = load_dataset("your/dataset-id")

# Prepare Trainer or custom loop here
```

When adapting such patterns to Kaggle:

- Pay attention to VRAM (batch sizes, sequence lengths).
- Use T4x2 with `device_map` if you need more capacity.
- Save intermediate adapters or checkpoints to `/kaggle/working`.

### 6.3 LLM fine-tuning on TPU (PyTorch/XLA)

For language models, TPUs can be attractive when:

- You need more aggregate memory and throughput than a single GPU.
- You are comfortable with PyTorch/XLA or JAX.

Key considerations:

- PyTorch/XLA has different performance characteristics than plain CUDA; you often need to tune input pipelines and patterns (e.g., static vs dynamic shapes).
- Some CUDA-only optimizations and libraries (FlashAttention, bitsandbytes) are not available on TPU, so the code path must fall back to native PyTorch + XLA.

A mapping strategy is:

- Start with a well-known example notebook (e.g., PyTorch/XLA on Kaggle or Google’s official TPU tutorials).
- Port your model to use XLA devices (`device='xla'` or `xm.xla_device()`).
- Add `notebook_launcher` for multi-core training.
- Benchmark and adjust batch sizes and learning rates.

### 6.4 Data management for LLMs on Kaggle

For LLM fine-tuning, datasets can be large (tens of GB). To handle them on Kaggle:

- Use **Hugging Face Datasets** with streaming mode where possible to avoid storing full datasets on disk.
- If using Kaggle Datasets, compress and split data sensibly (e.g., multiple JSONL or Parquet files).
- Consider using line-wise JSONL with a consistent schema (`{"instruction": ..., "input": ..., "output": ...}`) for instruction tuning.
- Regularly monitor disk usage and delete intermediate caches, especially for tokenized datasets.

## 7. Limitations, caveats, and when to move off Kaggle

### 7.1 Limits inherent to Kaggle

- **Quotas and runtime caps**: Weekly hour limits and per-session caps make very long runs difficult.
- **Shared environment**: Hardware and environment are shared; upgrades or breaking changes can occur without notice.
- **No root access**: You cannot fully customize kernel versions, drivers, or low-level system behavior.
- **Restricted networking**: Outbound network usage is generally allowed, but heavy download patterns may be throttled or limited; inbound ports are not exposed.

### 7.2 Practical implications for LLM work

- Very large models (30B, 70B, 100B+) are hard or impossible to fine-tune on Kaggle’s free accelerators.
- For large multi-experiment sweeps, Kaggle’s quotas will quickly become the bottleneck.
- Some advanced optimization libraries (e.g., specialized CUDA kernels, bleeding-edge quantization schemes) may not build or run correctly.

### 7.3 When to “graduate” to other platforms

Consider migrating to:

- **Google Cloud** (TPU v5e/v6e, A100/H100 GPUs) when you outgrow TPU v3–8 or need custom VMs.
- **RunPod, Lambda, Modal, or similar cloud providers** for flexible GPU clusters.
- **Hugging Face Inference Endpoints, Jobs, or Spaces with GPUs** when you want integrated model hosting and scheduled training.
- **On-prem or self-managed clusters** for long-lived research or production workloads.

Use Kaggle as an experimentation playground and proof-of-concept environment. Once a project requires sustained training time, reproducible large-scale experiments, or production SLAs, move to dedicated infrastructure.

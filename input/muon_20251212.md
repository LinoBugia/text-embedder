# Muon (Optimizer) Knowledge Base

## 0. Scope and terminology

This document is about **Muon**, the machine-learning optimizer, not the particle-physics muon.

Muon is commonly expanded as **MomentUm Orthogonalized by Newton–Schulz**. It targets **matrix-shaped parameters** (typically 2D weights in hidden layers) and post-processes a momentum update by **approximately orthogonalizing** it.

A recurring practical theme is **hybrid optimization**:
- Use **Muon** for matrix-heavy “hidden” weights.
- Use **AdamW (or similar)** for embeddings, layer norms, biases, and other non-matrix parameters.

## 1. Background and overview

### 1.1 What Muon does

Muon starts from an SGD-with-momentum style update. Then it transforms that update matrix so it becomes close to a **semi-orthogonal** matrix. Intuitively, it tries to avoid updates that are “too low-rank” or dominated by a small number of singular directions.

Key properties emphasized across sources:
- **Spectral balancing of updates**: orthogonalization makes update directions more uniform in magnitude.
- **Mixed-precision friendliness**: Newton–Schulz iterations can be run efficiently in BF16 in many implementations.
- **Different tradeoff than AdamW**: less optimizer-state memory than AdamW for matrix-heavy models, with some extra matrix compute.

### 1.2 Why “2D hidden layers” is repeated everywhere

Muon’s defining operation is a **matrix orthogonalization-like transform**. That maps naturally to parameters that are meaningfully “matrices” (e.g., linear layer weights). For vectors and scalars (biases, norm scales), the geometric meaning is weaker and typical recipes keep using AdamW-like methods.

## 2. Canonical definition and design (Keller Jordan, 2024)

Primary reference:
- Keller Jordan, “Muon: An optimizer for hidden layers in neural networks” (Dec 8, 2024):  
  https://kellerjordan.github.io/posts/muon/

### 2.1 Definition sketch

In Keller’s reference design:
1. Compute momentum update `G` for a 2D parameter.
2. Apply a Newton–Schulz iteration to map `G` to an approximately orthogonalized matrix.
3. Apply the resulting matrix update to the parameter.

Keller’s post provides a concrete PyTorch snippet for `newtonschulz5`, using tuned coefficients:
- `(a, b, c) = (3.4445, -4.7750, 2.0315)`
- Run ~5 steps in typical usage.
- Normalize the matrix before iterating.
- Transpose when the matrix is tall (rows > cols), apply the iteration, then transpose back.

### 2.2 Intuition: “nearest semi-orthogonal update”

Keller frames the operation as mapping an update matrix `G` to a nearby semi-orthogonal matrix (equivalent to `U V^T` if `G = U S V^T` is the SVD). This removes singular-value scaling and keeps directions.

The blog also discusses:
- Why SVD-based orthogonalization is too slow for training loops.
- Why Newton–Schulz is attractive: fast, stable enough in BF16 in practice, and tunable.

### 2.3 Practical scope rule

From the same writeup:
- Use Muon for **hidden 2D parameters**.
- Use AdamW (or similar) for embeddings, output heads, norms, and other parameters.
- Convolutional kernels can be adapted by flattening to a 2D matrix.

## 3. Scaling Muon to large LLM training (Moonshot AI / Kimi Team, 2025)

Primary reference:
- “Muon is Scalable for LLM Training” (arXiv:2502.16982):  
  https://arxiv.org/abs/2502.16982  
  HTML: https://ar5iv.labs.arxiv.org/html/2502.16982v1

### 3.1 Why scaling needs extra tricks

The Moonshot report identifies key gaps between small-scale Muon successes and large-scale LLM pretraining, then proposes fixes to make Muon “plug-in” to large runs.

Two techniques are highlighted as crucial:
1. **Add weight decay** (Muon originally omitted it in some early implementations).
2. **Adjust per-parameter update scaling** so different matrix shapes get comparable update RMS, and so Muon’s update scale can be matched to AdamW-like schedules.

The report explicitly positions these adjustments as ways to reduce hyperparameter retuning when switching from AdamW to Muon.

### 3.2 Distributed Muon (DP × TP) in the paper

The paper’s “Distributed Muon” is framed as:
- **ZeRO-1-style partitioning** of optimizer states across the *data-parallel* group.
- Extra steps compared with ZeRO-1 AdamW because Muon needs a **full matrix** to orthogonalize.

The paper describes two additional operations:
1. **DP gather**: gather gradient shards to form the full gradient matrix for a parameter.
2. **Compute full update**: run Newton–Schulz on the full matrix to produce the update, then keep only the local partition needed to update local shards.

This is the conceptual core behind the “communication-efficient” claim: the expensive full-matrix operations are organized so they do not require globally gathering across the entire world size when parallel groups are structured.

### 3.3 Reported outcomes

The Moonshot report includes scaling-law style experiments and claims compute-efficiency improvements versus AdamW under compute-optimal training conditions. It also introduces Moonlight (MoE models) trained with Muon.

Because “efficiency” depends heavily on the exact training recipe and cluster constraints, you should treat these as *evidence that Muon can scale*, not as a guarantee of universal dominance.

## 4. Official framework API: PyTorch `torch.optim.Muon`

Primary reference:
- PyTorch stable docs: https://docs.pytorch.org/docs/stable/generated/torch.optim.Muon.html

### 4.1 What the public API exposes

As shown in the PyTorch stable documentation, the constructor signature is:

`Muon(params, lr=0.02, momentum=0.95, weight_decay=0.0, nesterov=True)`

Implications:
- PyTorch’s exposed knobs are currently the “standard” ones: learning rate, momentum, weight decay, Nesterov.
- If you need deeper control over Newton–Schulz coefficients, steps, or custom scaling rules, you typically use a reference implementation (Keller-style) or a project-specific implementation (Moonshot-style).

### 4.2 Practical warning that still applies

Even with a native optimizer class, you still need **parameter grouping** so you apply Muon only to the intended 2D hidden-layer matrices, and something else to other parameters.

## 7. Implementation patterns and tips

### 7.1 Parameter grouping recipe (most important)

A robust default heuristic:
- Muon for parameters where `p.ndim == 2` and the parameter is a hidden weight matrix.
- AdamW (or other) for:
  - embeddings
  - output head / LM head
  - layer norms (RMSNorm / LayerNorm)
  - biases
  - any vector or scalar parameters

### 7.2 Recommended diagnostics

When experimenting with Muon, log:
- Weight norms and layer output RMS to detect runaway growth (weight decay matters at scale).
- Update RMS per layer.
- For a few representative matrices, singular-value spectra of gradients and updates.

For distributed Muon:
- Measure communication time directly using traces.
- Compare DP-only, TP-only, and hybrid DP×TP to find bottlenecks on your interconnect.

### 7.3 Typical hyperparameter starting points

From PyTorch’s public defaults:
- `momentum ≈ 0.95`
- `nesterov = True`
- `lr` default shown as `0.02`

From Keller’s design choices:
- ~5 Newton–Schulz steps
- tuned NS coefficients

From Moonshot’s scaling report:
- **weight decay** and **update-scale matching** are key to stability and schedule reuse.

## 8. Limitations, caveats, and open questions

- **Not a drop-in replacement for all parameters.** Hybrid setups are the norm.
- **Engineering complexity rises quickly** for distributed implementations.
- **Performance is hardware- and recipe-dependent.** Communication-efficient claims depend on DP/TP grouping, ZeRO strategy, and interconnect constraints.
- **Theory is still maturing.** There is active work on convergence analysis and variants, but best-practice recipes are still evolving.

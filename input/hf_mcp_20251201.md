# Model Context Protocol (MCP)

## 1. Background and overview

Model Context Protocol (MCP) is an open, vendor-neutral protocol that standardizes how large language model (LLM) applications connect to external tools, data sources, and automations. It defines a common way for assistants, IDEs, and other hosts to discover and invoke tools, read resources, and reuse prompt templates without custom integration for every tool and every model.

MCP uses JSON-RPC 2.0 over long-lived connections (stdio or HTTP/SSE) and introduces a small but powerful set of concepts:

- **Host** – the LLM application (desktop assistant, IDE extension, chat UI) that embeds an MCP client.
- **Client** – the MCP connector running inside the host, responsible for managing one or more MCP server connections.
- **Server** – any external process that exposes tools, resources, and prompts in a standardized way.

The current specification (version 2025-06-18) emphasizes security, structured tool output, and interactive flows between servers, hosts, and users. It adds detailed guidance on OAuth 2.1-based authorization, resource protection, and user-consent-driven flows so that powerful tools can be exposed safely to assistants.

MCP’s main promise is to solve the **N×M integration problem**: instead of building bespoke adapters between _N_ assistants and _M_ tools, both sides implement a single protocol. This makes the assistant ecosystem feel more like “USB-C for AI tools” rather than a mess of proprietary plugins.

## 2. Core concepts from the official specification

### 2.1 Actors and base protocol

From the official specification:

- **Hosts** initiate connections to servers and embed the LLM.
- **Clients** run inside the host and maintain JSON-RPC sessions with one or more servers.
- **Servers** provide capabilities (tools, resources, prompts) and respond to JSON-RPC requests.

Key aspects of the base protocol:

- **JSON-RPC 2.0** message format with request/response and notifications.
- **Stateful connections** so servers can maintain context (such as open resources or long-running operations).
- **Capability negotiation** so hosts and servers can discover what features the other side supports (sampling, tools, prompts, resources, etc.).

MCP takes inspiration from the Language Server Protocol (LSP): just as LSP made language tooling reusable across editors, MCP aims to make tools and context reusable across AI hosts.

### 2.2 Tools, resources, and prompts

MCP servers can expose three main kinds of capabilities:

1. **Tools**  
   Functions that can be invoked by the LLM through the host. Each tool has:
   - A unique name.
   - A human-readable description.
   - A JSON Schema describing its parameters and return type.

   Tools are how servers perform actions: query a database, call an API, run a computation, or trigger an automation. Because arguments and results are described via JSON Schema, hosts can validate inputs, enforce security checks, and use structured decoding on the model side.

2. **Resources**  
   Read-only or quasi-static data that provides context to the model or user, identified by URIs. Typical examples:
   - Files in a project.
   - Database schemas or configuration.
   - Help pages and documentation.

   The protocol standardizes how resources are listed, fetched, and linked (for example, through “resource links” that tie tool results back to resources).

3. **Prompts**  
   Server-side prompt templates that can be discovered and instantiated by clients. Prompts are parameterized and can include structured metadata. They allow servers to ship “prompt programs” alongside tools, so that different hosts reuse consistent instructions and workflows instead of copy-pasting prompt strings.

### 2.3 Client features: sampling, roots, and elicitation

The 2025-06-18 spec extends what clients can offer to servers:

- **Sampling** – servers can request that the host run the LLM on their behalf (server-initiated agentic behavior). This allows complex flows where a server uses the host’s model to reason, plan, or transform data, while still exposing tools and resources back to the host.
- **Roots** – servers can ask the host about boundaries in which they are allowed to operate (for example, a directory root or a URI namespace), improving safety and scoping.
- **Elicitation** – servers can ask the host to obtain more information from the user through interactive questions (for example, when a tool requires a missing argument or consent). This supports structured “accept / reject / cancel” flows and richer human-in-the-loop experiences.

Together, these features make MCP more than just “tool calling”: servers can take initiative, request samples, and negotiate context and permissions with the host, while still keeping the LLM under the host’s control.

### 2.4 Transports

MCP supports multiple transports:

- **stdio** – a process-based transport commonly used for local tools or servers running side by side with the host (e.g., a local CLI, editor extension, or desktop app).
- **HTTP / SSE** – a streamable HTTP transport for remote servers, suitable for production deployments (reverse proxies, load balancers, and cloud infrastructure). This is often how hosted services and multi-tenant MCP servers are exposed.

The protocol specifies how message framing works over each transport, but the logical JSON-RPC semantics are the same.

### 2.5 Security and trust & safety

Security is a first-class concern in the spec:

- **User consent and control** – users must explicitly consent to data access and tool usage; hosts should provide clear UIs for what is being shared and what each tool does.
- **Data privacy** – hosts must treat resource data as sensitive and avoid sending it to arbitrary servers or models without consent.
- **Tool safety** – tools are arbitrary code execution paths; hosts should treat tool descriptions as untrusted unless servers are trusted, and may require explicit confirmation for impactful actions.
- **LLM sampling controls** – servers can request sampling, but hosts decide whether, how, and what prompts are shared; servers see only what the host chooses to expose.

The spec also adds implementation guidelines and “security best practices” pages, recommending scoped tokens, access control, logging, and documentation of security implications.

## 3. Hugging Face + MCP

Hugging Face participates in the MCP ecosystem in both server and client roles, and its documentation and blog posts provide rich practical examples.

### 3.1 Hugging Face MCP Server (hf-mcp-server)

The **Hugging Face MCP Server** is a hosted MCP server that connects MCP-compatible clients directly to the Hugging Face Hub. Once configured, an assistant inside VS Code, Cursor, Zed, Claude Desktop, or other hosts can:

- Search and explore models, datasets, Spaces, and papers on the Hub.
- Run community tools exposed by MCP-enabled Gradio Spaces.
- Bring back results with titles, owners, descriptions, and links into the chat or editor.

Configuration is driven through the Hugging Face MCP settings page:

1. Go to `https://huggingface.co/settings/mcp` while logged in.
2. Choose your client (e.g., VS Code, Cursor, Claude Desktop).
3. Copy the generated configuration snippet into the client’s MCP configuration file.
4. Restart the client so it connects to the Hugging Face MCP Server and loads its tool catalog.

From there, you can simply prompt your assistant with requests like “Search Hugging Face models for Qwen 3 quantizations” or “Find a Space that can transcribe audio files”, and the assistant will call the appropriate MCP tools hosted by Hugging Face.

### 3.2 Spaces as MCP servers (Gradio + ZeroGPU)

Hugging Face Spaces (especially Gradio Spaces) can themselves act as MCP servers. The general pattern is:

- Build a Gradio app as usual (Blocks, Interfaces, etc.).
- Start it with `demo.launch(mcp_server=True)` (or the equivalent flag).

This makes the Space expose an MCP server alongside the Gradio UI. A concrete example is the **TRELLIS** Space, a ZeroGPU Gradio app for 2D-to-3D generation. Under the hood:

- The app defines a function like `generate_and_extract_glb(...)` wired to a UI button.
- It runs on ZeroGPU with `@spaces.GPU(duration=...)` decorators.
- The Gradio app is exposed at `https://<space-id>.hf.space`, where the regular HTTP queue API (`/call/<fn>`, SSE responses) can be used by tools like n8n.
- With `mcp_server=True`, the same Space also exposes an MCP server, so IDEs or assistants can call the underlying function as an MCP tool instead of manually driving the Gradio HTTP API.

This pattern is powerful because it lets you:

- Prototype interactive tools in Gradio.
- Expose them to humans via the UI and to agents via MCP, with a single codebase.
- Optionally run them on ZeroGPU for low-cost experiments, while still using them as tools in MCP-capable hosts.

## 4. Your Document AI + MCP stack

Your Document AI stack is a good example of using MCP not just for “toy tools,” but for a multi-stage, production-minded pipeline. Conceptually, you split the problem into four concerns: normalization, routing, extraction, and action. MCP then provides a clean way to expose each concern as tools to agents and UIs.

### 4.1 Deterministic document normalization

First, every incoming file (PDF, DOCX, EML/MSG, image, etc.) is normalized into a stable internal representation **before** any LLM is involved:

- **Docling** is used as the primary normalizer, producing structured representations (Markdown, HTML, JSON) with reading order, table structure, and layout metadata.
- **Unstructured** is used when dealing with unusual formats or emails (EML/MSG), providing typed elements and metadata.
- For OCR-heavy scans and complex tables, Docling’s own layout capabilities or OCR frameworks like PaddleOCR PP-Structure can be used as fallbacks.

The result is a deterministic “doc proto” that downstream stages can rely on. Exposed via MCP, you might have tools like:

- `normalize_document` – accept a file path or blob reference, return structured JSON + Markdown.
- `inspect_document_layout` – return layout blocks, tables, and figures for downstream routing.

### 4.2 Typed extraction with strict schemas

Extraction is performed with **strict JSON schemas**, enforcing reproducible outputs:

- You define per-document-type models (e.g., `Invoice`, `BankStatement`, `InsuranceLetter`) using Pydantic.
- For each schema, you generate JSON Schema artifacts used by constrained decoding libraries like **LM-Format-Enforcer** or Outlines.
- A small LLM (Qwen2.5, Phi-4, or similar) runs in a mapping role: given the normalized doc and a schema, it fills in the fields, but the schema and decoder enforce valid types and structure.

Within MCP, you can implement tools like:

- `extract_invoice_fields` – accepts normalized invoice JSON, returns an `Invoice` JSON object matching the Pydantic schema.
- `validate_extraction` – re-validate or repair extracted data (check digits, IBAN/VAT regexes, etc.).

By pushing layout and OCR into Docling and friends, and constraining the LLM’s output, you avoid the “same prompt, different shape” problem and reduce hallucinations.

### 4.3 Rule-based action routing

After extraction, actions are determined by deterministic business rules, not by the LLM:

- Rules are implemented via JSONLogic or simple Python predicates on the extracted JSON.
- Examples:
  - `IF type == "Invoice" AND total >= 1000 THEN notify finance AND enqueue ERP update`.
  - `IF type == "Receipt" AND sender_domain in allowlist THEN auto-file to the receipts folder`.

You can expose these as MCP tools as well:

- `decide_actions_for_document` – accept extracted JSON and return a list of actions.
- `execute_action` – execute an action (e.g., write to a DB, trigger a webhook), potentially gated by human approvals.

This separation keeps the pipeline auditable: normalization and extraction are deterministic or constrained; actions are explicit and rule-based.

### 4.4 Email pipelines and ingestion

For emails you rely on provider-native push and change-notification APIs:

- **Gmail** `users.watch` + Pub/Sub to subscribe to changes, download messages and attachments, and feed them into the same normalization pipeline.
- **Microsoft 365** change notifications via Microsoft Graph to detect new or changed messages.

MCP servers can sit at the boundary:

- An “email ingestion” server exposes tools like `list_new_messages`, `download_message`, or `download_attachments`.
- The Document AI server provides normalization and extraction tools.
- A higher-level orchestrator (agent or workflow engine) chains these tools together, but each piece remains independently testable and replaceable.

### 4.5 Operator UI and human-in-the-loop

On top of the pipeline, you run operator UIs such as **OpenWebUI**, which can:

- Act as a host connecting to MCP servers (filesystem, Document AI, DB, email).
- Expose pipelines via OpenWebUI Functions or Pipelines, turning them into OpenAI-compatible endpoints that MCP-based agents can also call.
- Integrate with LangGraph or similar graph frameworks to provide human approvals (“interrupts”) where certain MCP tools require confirmation before execution.

MCP Inspector and similar tools help debug and document MCP servers, showing tool schemas, sample calls, and outputs.

## 5. Agent architecture with MCP tools

Your agent architecture focuses on latency, parallelism, and safety, using MCP tools as the execution layer.

### 5.1 Two-speed architecture: router and micro-planner

To keep turn times around 2–3 seconds while maintaining accuracy, you use a **two-speed agent**:

1. **Router (cheap model)**  
   - Classifies incoming turns as `single_tool`, `multi_step`, or `clarify`.
   - If `single_tool`, it picks the tool and arguments directly (using structured decoding).
   - If `clarify`, it asks exactly one follow-up question and then re-runs routing.

2. **Micro-planner (larger model, only when needed)**  
   - Runs only when the router decides the turn is `multi_step`.
   - Produces a small **DAG** of at most a handful of steps with explicit dependencies (`after` edges).
   - Specifies which MCP tools to call and with which arguments; unknown arguments are surfaced as clarification needs instead of being hallucinated.

This division avoids running a heavy planner on every single turn and keeps planning bounded.

### 5.2 Graph executor and parallel MCP calls

A **graph executor** runs the DAG:

- Nodes representing MCP tool calls are scheduled as soon as their dependencies are resolved.
- Independent nodes are executed in parallel, which is critical when combining multiple retrieval, database, or Document AI tools.
- The executor checkpoints state after each batch of tool calls so that it can recover from failures, retry selectively, or support human-in-the-loop corrections.

MCP sits at the edge:

- Every tool is defined with JSON Schema, and arguments are validated before being sent.
- For risky tools (sending emails, wiring money, modifying production DBs), the executor can pause and require a human confirmation (“interrupt”) before actually invoking the MCP call.

### 5.3 Serving stack and structured decoding

On the LLM serving side, you can use infrastructure such as vLLM or SGLang with:

- **Automatic prefix caching** to reuse the system prompt and tool table across calls.
- **Structured outputs** to ensure plans and tool-argument JSON strictly follow schemas.
- Continuous batching and speculative decoding for throughput.

This combination allows you to:

- Encode router decisions and micro-plans as JSON objects (no free-form text).
- Generate arguments for a whole parallel batch of tools in one LLM call.
- Avoid repair loops caused by invalid JSON, since the decoder and validators enforce structure up front.

### 5.4 Security and MCP tool governance

Security-wise, you align with MCP’s own guidance:

- **Validate every tool call** against JSON Schema at the MCP edge.
- **Apply rate limiting and timeouts** per tool and per user.
- **Log all tool calls and results** with enough detail for audits, without leaking sensitive data.
- **Gate high-impact tools** with human approvals via interrupts or explicit confirmation prompts.

Seen as a whole, MCP becomes the “interop and safety boundary”: tools live behind MCP servers with schemas and governance, while the agent stack focuses on planning and orchestration.

## 6. Implementation patterns and tips

### 6.1 When to build an MCP server

Build an MCP server when:

- You want your capability to be usable from many MCP-capable hosts (VS Code extensions, desktop assistants, custom applications) without writing adapters.
- Your tool needs to expose multiple operations, resources, or prompts with consistent schemas.
- You care about governance, logging, and security at the integration boundary.

Using a plain HTTP API might be enough when you control both client and server and do not expect reuse across hosts. MCP really shines when you want your tool to be part of a larger ecosystem.

### 6.2 Server structure and configuration

Common patterns for MCP servers (seen in community examples and documentation):

- Repository layout:
  - `src/server.ts` or `src/main.py` implementing the MCP server logic.
  - `mcp.json` or similar for configuration (names, transports, ports).
  - Tests and example clients in a separate folder.
- Use the official MCP SDKs (TypeScript/Node, Python) where possible instead of hand-rolling JSON-RPC.
- Provide clear documentation of exposed tools, resources, and prompts, including examples and expected schemas.

Gradio Spaces that act as MCP servers inherit a lot of this structure from Gradio itself; the main addition is enabling `mcp_server=True` and carefully designing input/output types for the underlying functions.

### 6.3 Schema and UX design

A few practical tips for schema design and user experience:

- **Small, composable tools** – prefer multiple focused tools instead of one mega-tool with many optional fields.
- **Explicit enums and constraints** – use enums, regex patterns, and numeric ranges in JSON Schema to guide models and prevent invalid calls.
- **Human-readable descriptions** – tool descriptions, parameter docs, and prompt titles should be terse but clear, since they are read by humans and models alike.
- **Resource links** – where relevant, include resource URIs in tool results so that hosts can open files or documents directly.

### 6.4 Observability and testing

To keep confidence high:

- Use MCP Inspector or similar tools to manually browse and call your MCP server during development.
- Add automated tests that run your server in a local mode and execute tool calls against golden inputs.
- Record example sessions (requests, responses, tool arguments) and replay them for regression testing when you change schemas or upgrade SDKs.

### 6.5 Performance and cost

When performance matters:

- Avoid unnecessary LLM calls by caching tool results keyed by `(tool, normalized_args)`.
- Use a fast router model and reserve heavier models for planning or difficult extraction tasks.
- For CPU-only environments, offload structure-heavy tasks to specialized models (like document parsers or embedding models) and keep the LLM focused on mapping and reasoning.

## 7. Limitations, caveats, and open questions

Although MCP is rapidly gaining adoption, several caveats remain:

- **Security is not automatic** – the protocol cannot enforce safe behavior by itself; implementors must design proper consent flows, scoping, and access controls.
- **Prompt injection and tool misuse** – LLMs can still be tricked into calling tools with harmful arguments; schema validation, allowlists, and human approvals are still needed for sensitive operations.
- **Ecosystem maturity** – while major assistants and IDEs are adopting MCP, host-side UIs and configuration flows are still evolving, and not all features (sampling, elicitation) are supported everywhere yet.
- **Versioning and compatibility** – servers and hosts may implement different spec versions or optional features; robust capability negotiation and backwards-compatible schemas are important.
- **Operational complexity** – large deployments with many tools and users require logging, monitoring, multi-tenant isolation, and incident response, just like any other production API.

Despite these challenges, MCP is currently the most widely recognized open standard for connecting LLM applications to tools and data, and its combination of structured schemas, security guidance, and host–server separation makes it a strong foundation for your Document AI and agentic systems.

### 8.1 Minimal MCP server (sketch)

At a high level, a minimal MCP server in Python might:

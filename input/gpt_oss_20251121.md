# GPT-OSS: OpenAI's open-weight reasoning model family

## 1. Background and overview

### 1.1 What GPT-OSS is

GPT-OSS is an open-weight large language model (LLM) family released by OpenAI in 2025 as its first openly available language models since GPT-2. The family currently consists of two text-only models:

- **gpt-oss-120b** – a large, high-reasoning mixture-of-experts (MoE) model with 117B total parameters and about 5.1B active parameters per token.
- **gpt-oss-20b** – a smaller, more deployable MoE model with 21B total parameters and about 3.6B active parameters per token.

Both models:

- Are **open-weight**, not fully open-source: you can download the trained weights, run them locally, and fine-tune them, but the full training data is not published.
- Are released under the **Apache 2.0 license**, which permits commercial use, redistribution, and derivative models, subject to minimal policy constraints.
- Target **reasoning, coding, and agentic workflows**: they are optimized for chain-of-thought reasoning, tool use, and structured responses.
- Are designed for **wide deployment**: from a single 80 GB data-center GPU for gpt-oss-120b to ~16 GB-class consumer hardware for gpt-oss-20b (via quantization and local runtimes).

Conceptually, GPT-OSS sits alongside other open-weight LLM families (Llama, Qwen, DeepSeek, Gemma, GLM, etc.), but is distinguished by being an official OpenAI release with a strong focus on reasoning, safety, and on‑device deployment.

### 1.2 Model variants at a glance

From the official model card and launch materials, the two variants can be summarized as:

| Model           | Total params | Active params / token | Layers | Experts | Active experts | Context length | Typical hardware target |
|----------------|-------------:|----------------------:|-------:|--------:|---------------:|----------------|-------------------------|
| gpt-oss-120b   | 117B         | ~5.1B                 | 36     | 128     | 4              | 128k tokens    | Single 80 GB GPU (H100, MI300X) |
| gpt-oss-20b    | 21B          | ~3.6B                 | 24     | 32      | 4              | 128k tokens    | ~16 GB VRAM class devices; laptops / workstations via quantization |

Key shared characteristics:

- **Mixture-of-experts Transformer**: the model alternates dense layers with MoE layers, activating only a subset of experts per token to save compute while keeping capacity high.
- **Long context**: both models support context lengths around **128k tokens**, which is unusually large for models that can run locally.
- **Harmony tokenizer and format**: both use the **o200k_harmony** tokenizer and a matching “harmony” response format with explicit control tokens for roles, structure, and chain-of-thought.

### 1.3 Why GPT-OSS matters in the open ecosystem

GPT-OSS is notable because it:

- Marks OpenAI’s **return to open-weight models**, directly competing with other open families.
- Provides **strong reasoning models** whose weights can be inspected, fine-tuned, distilled, quantized to GGUF, and run in local runtimes such as `llama.cpp` or vLLM.
- Comes with **tooling from both OpenAI and Hugging Face** (model cards, recipes, Unsloth guides, GGUF conversions), making it easy to integrate into existing pipelines.

For practitioners already fine-tuning open LLMs, GPT-OSS is effectively “another base family” to consider, with the usual trade‑offs: quality vs hardware, alignment vs freedom, and ecosystem maturity vs performance.

### 2.1 OpenAI’s “Introducing gpt-oss”

  - GPT-OSS models are trained with OpenAI’s most advanced pre‑training and post‑training techniques, with a strong focus on **reasoning quality**, **efficiency**, and **real‑world usability** across varied hardware.
  - The data is primarily high‑quality **English text**, with a strong emphasis on **STEM**, **coding**, and **general knowledge** domains.

- **Architecture**  
  - Both models are **Mixture-of-Experts Transformers**, with:
    - Alternating dense and MoE layers.
    - A gated router that selects a small number of experts for each token.
  - They use advanced attention variants such as **grouped multi‑query attention** and **banded sparse attention** to improve speed and memory usage at long context lengths.

    - Explicit delimiters for roles (`system`, `user`, `assistant`, `tool`).

## 5. Implementation patterns and tips

This section focuses on **practical usage, fine-tuning, and deployment patterns** for GPT-OSS, especially within the Hugging Face ecosystem and common local-LLM stacks.

### 5.1 Basic inference via Transformers and vLLM

At a minimum, you can treat GPT-OSS like any other causal LM on Hugging Face:

```python
from transformers import AutoTokenizer, AutoModelForCausalLM

model_id = "openai/gpt-oss-20b"  # or "openai/gpt-oss-120b"

tokenizer = AutoTokenizer.from_pretrained(model_id)
model = AutoModelForCausalLM.from_pretrained(
    model_id,
    torch_dtype="auto",  # match weights
)

prompt = "You are a helpful assistant. Explain what GPT-OSS is in simple terms."
inputs = tokenizer(prompt, return_tensors="pt")

outputs = model.generate(
    **inputs,
    max_new_tokens=256,
    do_sample=True,
    temperature=0.7,
)
print(tokenizer.decode(outputs[0], skip_special_tokens=True))
```

However, to get **best results**, you should:

- Use the **harmony chat format** instead of a raw prompt, following examples from the OpenAI GitHub repo and model cards.
- For high-throughput or multi-request setups, use **vLLM** or **Text Generation Inference (TGI)** rather than hand‑rolled scripts.
- If you need long-context usage (tens of thousands of tokens), carefully configure:
  - KV cache memory.
  - Attention implementation (e.g., vLLM’s paged attention).
  - Maximum sequence length and batching policy.

For production, always benchmark your configuration with realistic prompts, not just tiny quick-start examples.

### 5.2 Using harmony formatting and chain-of-thought

Since GPT-OSS is trained on harmony-formatted conversations, you should:

1. Adopt a **structured message format** with explicit roles (system, user, assistant, tool).
2. Use official or community-provided **chat templates** that map lists of messages into token sequences.
3. When you want chain-of-thought reasoning:
   - Use flags or system instructions that request reasoning.
   - Optionally keep reasoning in a **separate channel** (e.g., tool or hidden role) and only show final answers to end users.
4. When using tool calls:
   - Provide clear JSON schemas and function descriptions.
   - Let GPT-OSS propose tool calls, then execute them externally and feed results back via a `tool` role.

Harmony formatting is not just a cosmetic choice: the model was explicitly trained with it, so deviating strongly from the format usually reduces performance and reliability.

### 5.3 Fine-tuning GPT-OSS: strategy and constraints

From a fine-tuning perspective, GPT-OSS is “just another” causal LM, but with practical considerations:

- **Model size and MoE**  
  - The 20B and 120B sizes mean full-model fine-tuning is extremely expensive.
  - MoE architectures need carefully tuned parallelism and memory layouts; not all training frameworks fully support them out of the box.

- **Recommended approach**  
  - Use **adapter-based methods (LoRA / QLoRA)**:
    - For **gpt-oss-20b**, LoRA on attention and MLP layers is feasible with high-end single GPUs or small multi-GPU setups.
    - For **gpt-oss-120b**, LoRA is typically multi-GPU or cluster-scale work; expect to rely on data-parallel and tensor-parallel schemes.
  - Follow general LLM fine-tuning best practices:
    - High-quality, well-formatted datasets (instruction/chat or domain text).
    - Conservative learning rates and careful monitoring for instability.
    - Validation on both task-specific benchmarks and general ability benchmarks to avoid over-specialization.

- **Library choices**  
  - **Transformers + TRL** for SFT, DPO/ORPO, and RL-style training.
  - **Unsloth** for optimized QLoRA and GGUF export; their GPT-OSS docs contain tuned configs.
  - **Custom Accelerate / DeepSpeed** stacks for institutions with bespoke training needs.

### 5.4 Example LoRA/QLoRA recipe sketch (20B model)

A concrete (but high-level) LoRA/QLoRA plan for `gpt-oss-20b`:

1. **Base model**  
   - Start from `openai/gpt-oss-20b` BF16 or a 4‑bit quantized variant.
2. **Data**  
   - Prepare a clean dataset in `messages` or `instruction`/`output` format with:
     - Clear instruction, context, and answer sections.
     - Harmony-like formatting if you plan to keep the model in harmony format.
3. **Adapter configuration**  
   - LoRA rank in the range **8–64**, targeting attention and MLP modules.
   - Use QLoRA (4‑bit base weights + LoRA adapters) where VRAM is tight.
4. **Training**  
   - Optimizer: AdamW or Lion with a moderate learning rate (e.g., 1e‑4 to 2e‑4 for adapters).
   - Sequence length: respect the tasks; you rarely need the full 128k for training.
   - Monitor training loss and validation metrics; inspect sample generations frequently.
5. **Export**  
   - Merge the LoRA into BF16 weights if you want a single consolidated model.
   - Convert to GGUF or ONNX for deployment via llama.cpp, vLLM, or Inference Endpoints.

Fine-tuning GPT-OSS should follow the same discipline as other large LLMs: **start small, validate often, and iterate primarily on data quality** rather than constantly tweaking hyperparameters.

## 6. Limitations, caveats, and open questions

### 6.1 Model limitations and community feedback

Despite strong benchmarks, GPT-OSS has practical limitations:

- **Knowledge coverage**  
  - As with other LLMs, GPT-OSS has a fixed knowledge cutoff and may underperform on very recent topics or niche domains not represented in its training data.
- **Domain balance**  
  - The training focus on STEM and coding means some users perceive weaker performance in softer domains (literature, arts, nuanced social topics) relative to some competitor models.
- **Safety vs openness**  
  - Strong alignment and safety tuning lead some users to describe the models as “too cautious” or “lobotomized” in uncensored contexts.
  - Many community fine‑tunes explicitly aim to **reduce refusal behavior**, which can be desirable for some tasks but carries obvious safety risks.

These trade-offs are similar to those seen in other open-weight models, but the **OpenAI provenance** makes safety considerations especially salient.

### 6.2 Hardware and scaling caveats

Some practical hardware caveats when working with GPT-OSS:

- **Inference**  
  - While 20B can run on 16 GB devices with aggressive quantization, performance may be borderline on low‑end hardware.
  - 120B remains a **data-center-class model**; even with MoE and quantization, it demands substantial GPU memory and bandwidth.
- **Training and fine-tuning**  
  - VRAM requirements for fine-tuning can be much higher than for inference, especially if you unfreeze large portions of the model.
  - MoE architectures put additional stress on communication and memory; not all training stacks are equally mature here.
  - Many practitioners stick to **adapter-based fine-tuning** and avoid full-model updates.

You should prototype configurations with **small experiments** before committing to large-scale runs, and pin working stacks (hardware + drivers + CUDA/ROCm + PyTorch + kernels) to avoid regressions.

### 6.3 Safety, governance, and derivative models

Because GPT-OSS weights are open:

- Enterprises can build **fully on-premise deployments**, keeping data inside their own infrastructure.
- Researchers can inspect, probe, and analyze the models (e.g., expert activation patterns, safety behaviors) in ways that closed models do not allow.
- At the same time, community derivatives can:
  - Remove safety filters.
  - Add potentially harmful capabilities through targeted fine-tuning.

For production deployments, especially in sensitive domains (health, finance, critical infrastructure), you should:

- Treat **safety evaluation as a first-class task** (internal red-teaming, audits, domain-specific benchmarks).
- Maintain **governance over which variants** (official vs community fine-tunes) are allowed in your infrastructure.
- Log and monitor model behavior over time, rather than assuming “open + Apache 2.0” implies risk-free usage.

### 6.4 Open questions and evolving ecosystem

Several aspects of GPT-OSS are still evolving:

- **Best practices for long-context usage** (128k prompts) in real workloads, including memory-efficient RAG and agent orchestration.
- **Fine-tuning recipes for stability** on MoE architectures at this scale, especially for multi-GPU and multi-node setups.
- **Comparisons with future open-weight releases** (from OpenAI and others), as the ecosystem moves quickly and new models appear.

Because of this, it is important to track:

## 8. Fine-tuning GPT-OSS-20B on a single A100-80GB GPU (OOM case study)

### 8.1 What went wrong in the A100-80GB run

In a single-GPU setup using an NVIDIA A100-80GB, GPT-OSS-20B was fine-tuned with TRL's `SFTTrainer` in bf16 with LoRA adapters and the following key settings:

- `per_device_train_batch_size=4`
- `gradient_accumulation_steps=4`
- `max_length=1024`
- `attn_implementation="eager"`
- Base weights loaded from an MXFP4 checkpoint but dequantized to bf16 on GPU

GPT-OSS-20B has 21B total parameters, about 3.6B active parameters per token, 24 layers, 64 attention heads, and 32 MoE experts (4 active per token). During training, the eager attention implementation in Transformers computed a full attention tensor of shape:

- `[B, num_heads, L, L] = [4, 64, 1024, 1024]`

This corresponds to 268,435,456 bf16 values, or roughly **512 MiB** for a single `attn_weights` tensor. At the point where this allocation was requested, the GPU already had about 79 GiB in use, leaving only a few hundred MiB free plus some fragmented "reserved but unallocated" memory. The allocator could not find a contiguous 512 MiB block, and PyTorch raised a `CUDA out of memory` error.

### 8.2 Why this is expected for bf16 LoRA on GPT-OSS-20B

Several factors make this configuration extremely memory-hungry:

- **Large bf16 base model** – Dequantizing the 4-bit MXFP4 checkpoint to bf16 puts the base weights alone in the ~40–50 GiB range on GPU.
- **MoE overhead** – GPT-OSS-20B is a Mixture-of-Experts model, so activations include expert-specific buffers and router state, in addition to standard Transformer activations.
- **Quadratic attention** – With eager attention, the training code effectively pays an L×L cost in memory for attention weights at each layer, and for L=1024 this quickly becomes large even at small batch sizes.
- **Additional training state** – On top of weights and activations, memory is needed for gradients (or recomputation metadata under gradient checkpointing), LoRA adapters, and optimizer state.

On H100-80GB hardware, the official cookbook recipe shows that bf16 LoRA training with `per_device_train_batch_size=4` and `max_length=2048` can work, but that setting is right at the limit even there. On an A100-80GB, the same configuration leaves little safety margin and is prone to OOM when memory becomes fragmented.

### 8.3 A safer bf16 LoRA configuration for A100-80GB

To keep GPT-OSS-20B bf16 LoRA fine-tuning within the practical limits of a single A100-80GB, it is advisable to reduce both the instantaneous batch size and sequence length, while compensating with gradient accumulation:

```python
from trl import SFTConfig

training_args = SFTConfig(
    # Core optimization
    learning_rate=2e-4,
    num_train_epochs=1,
    warmup_ratio=0.03,
    lr_scheduler_type="cosine_with_min_lr",
    lr_scheduler_kwargs={"min_lr_rate": 0.1},

    # Memory-critical knobs
    per_device_train_batch_size=1,   # reduce instantaneous batch
    gradient_accumulation_steps=16,  # keep effective batch ≈ 16
    max_length=512,                  # start low; increase cautiously
    gradient_checkpointing=True,
    bf16=True,
    fp16=False,

    # Logging and outputs
    logging_steps=1,
    report_to=None,
    output_dir="gpt-oss-20b-a100-bf16-lora",
)
```

Practical recommendations:

- Start with `per_device_train_batch_size=1` and `max_length=512`. Only increase to 768 or 1024 after confirming that a full training step completes without OOM.
- Monitor VRAM usage with `nvidia-smi` or similar tools and ensure peak memory stays several GiB below 80 GiB.
- Ensure the model is loaded with `use_cache=False` during training to avoid extra KV cache allocations.
- Avoid `torch.compile` (Dynamo) while debugging OOM issues, as graph capture can temporarily increase memory usage or make failures harder to interpret.

### 8.4 Reducing fragmentation with PyTorch CUDA allocator settings

When OOM errors occur despite there being substantial "reserved but unallocated" memory, fragmentation is often the real problem. In these cases, tuning PyTorch's CUDA allocator can help:

```bash
export PYTORCH_CUDA_ALLOC_CONF="expandable_segments:True,max_split_size_mb:512"
python train_gpt_oss_20b.py
```

- `expandable_segments:True` encourages larger, growable memory segments, which reduces fragmentation of big blocks.
- `max_split_size_mb:512` prevents very large allocations from being repeatedly split, making it easier to allocate another 512 MiB block later.

These settings do not increase the total available VRAM, but they can prevent failures where a large tensor cannot be placed because memory is badly fragmented.

### 8.5 Switching to 4-bit QLoRA with Unsloth

For most users, especially if you want longer sequences or larger effective batch sizes, moving from bf16 LoRA to **4-bit QLoRA** is a more robust and scalable approach. Unsloth provides GPT-OSS checkpoints and kernels that are specifically optimized for this use case.

A typical Unsloth-based QLoRA setup for GPT-OSS-20B looks like:

```python
from unsloth import FastLanguageModel

max_seq_length = 1024

model, tokenizer = FastLanguageModel.from_pretrained(
    "unsloth/gpt-oss-20b",   # or "unsloth/gpt-oss-20b-unsloth-bnb-4bit"
    max_seq_length=max_seq_length,
    load_in_4bit=True,       # QLoRA: 4-bit base weights
    full_finetuning=False,   # adapter-based tuning only
)

model = FastLanguageModel.get_peft_model(
    model,
    r=8,
    lora_alpha=16,
    target_modules=[
        "q_proj", "k_proj", "v_proj", "o_proj",
        "gate_proj", "up_proj", "down_proj",
    ],
    lora_dropout=0,
    use_gradient_checkpointing="unsloth",
)
```

Key characteristics of this approach:

- Base weights are stored in 4-bit (e.g., bitsandbytes NF4), dramatically reducing VRAM consumption compared to bf16.
- Only the small LoRA adapter matrices are trained in 16-bit precision, keeping the number of trainable parameters low.
- Unsloth's custom attention kernels further reduce VRAM usage and enable longer context lengths without OOM.
- After training, you can merge the adapters into bf16 or MXFP4 weights and export to formats suitable for Transformers, vLLM, GGUF (llama.cpp), and other runtimes.

On a single A100-80GB, QLoRA with Unsloth typically leaves ample headroom for sequences of 1k–2k tokens and moderate batch sizes, making it a safer default than bf16 LoRA when you are not constrained by training time alone.

### 8.6 A practical checklist for GPT-OSS-20B training on A100-80GB

When planning or debugging a training run on a single A100-80GB, use the following checklist:

1. **Choose the regime** – Decide explicitly between bf16 LoRA and 4-bit QLoRA. For most scenarios, QLoRA (with Unsloth) is the recommended starting point.
2. **Control instantaneous batch size and sequence length** – Begin with `per_device_train_batch_size=1` and `max_length=512`, then scale up only after verifying stability.
3. **Enable gradient checkpointing** – Trade compute for memory to make room for activations and attention buffers.
4. **Be aware of attention implementation details** – Eager attention for GPT-OSS may not fully exploit sliding-window or banded sparse patterns during training yet, so avoid very long sequences in bf16.
5. **Tune the CUDA allocator** – Use `PYTORCH_CUDA_ALLOC_CONF` to mitigate fragmentation when you are close to the VRAM limit.
6. **Keep the software stack simple while debugging** – Avoid `torch.compile`, unnecessary callbacks, and heavy logging until you have a clean, reproducible run.
7. **Run short pilot experiments** – Test with a small subset of data and a handful of steps before committing to full epochs or large-scale jobs.

Large MoE models like GPT-OSS-20B can be trained on a single A100-80GB, but doing so reliably requires treating precision, quantization, batch size, sequence length, and allocator settings as first-class design choices rather than afterthoughts.

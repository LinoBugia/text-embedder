## 1. Background and overview

AMD’s GPU ecosystem for AI has grown into three main pillars:

- **Datacenter accelerators (AMD Instinct)** – MI200 and MI300 series GPUs targeted at large language models (LLMs), high‑throughput inference, and training in data centers.

- **Ryzen AI NPUs and APUs** – integrated accelerators in mobile CPUs and small form‑factor devices used for lightweight inference and on‑device assistants.

On the software side, AI on AMD is enabled via several stacks:

- **ROCm** – AMD’s CUDA‑like platform providing HIP, libraries, and drivers for Linux (and, increasingly, Windows). It underpins PyTorch ROCm, TensorFlow ROCm, and many HPC/AI libraries.

- **ONNX Runtime (ORT) Execution Providers** – ROCm EP on Linux and DirectML EP on Windows enable cross‑vendor acceleration, including AMD GPUs.
- **Other layers** – llama.cpp / GGML for CPU and generic GPU backends, ZLUDA to run CUDA‑oriented apps on AMD GPUs, and DirectML extensions for popular UIs.

## 3. Software stacks for AMD + AI

### 3.1 ROCm and PyTorch ROCm

**ROCm** (Radeon Open Compute) is AMD’s GPU compute platform, analogous to CUDA. For AI workloads:

- PyTorch ROCm wheels expose `torch.cuda.is_available()` and the `"cuda"` device string even on AMD, but behind the scenes use **HIP** and ROCm libraries. This is a common source of confusion; `torch.version.cuda` may be `None`, while `torch.version.hip` is set.
- ROCm versions are tightly coupled to GPU, OS, and kernel versions. Mismatched combinations often manifest as build errors, silent CPU fallbacks, or unstable performance.

The recommended setup on Linux is:

1. Choose your target **ROCm version** based on the compatibility matrix.
2. Install drivers and ROCm according to AMD’s official install guide.
3. Use the PyTorch “Get Started” selector to install **matching ROCm wheels**.
4. Validate with `rocminfo` and a minimal PyTorch script that allocates a tensor on `"cuda"`.

The AMD + Hugging Face docs add a few points:

- For **HF Transformers and Diffusers**, ordinary CUDA‑style code generally works unchanged when using ROCm wheels.
- For **Optimum‑AMD**, specialized kernels and runtime options exist for Instinct GPUs and Ryzen AI NPUs.

### 3.3 ONNX Runtime (ROCm EP and DirectML EP)

**ONNX Runtime (ORT)** supports multiple execution providers (EPs):

- **ROCMExecutionProvider** – accelerates ONNX models on AMD Instinct GPUs with ROCm on Linux. Hugging Face Optimum‑ONNX provides simple adapters to run Transformers via ORT + ROCm EP.
- **DirectML Execution Provider** – accelerates ONNX models on Windows using **DirectML**, which works on AMD, Nvidia, and Intel GPUs through a unified API. This is particularly useful on Windows with Radeon GPUs where ROCm is not yet fully supported.

Typical patterns:

- On Linux with Instinct or supported Radeon: use **ROCMExecutionProvider** via Optimum‑ONNX or ORT directly, plus ROCm drivers.
- On Windows with Radeon: use **DirectML EP** for Stable Diffusion and lightweight LLMs, often via UIs like SD.Next that expose an “ONNX + DirectML” mode.
- For cross‑platform portability: export a model to ONNX and select the appropriate EP (CUDA, ROCm, DirectML) at runtime.

### 3.4 Windows‑specific stacks: DirectML, ZLUDA, ROCm for Windows, WSL2

On Windows, you have several ways to use AMD GPUs for AI:

1. **ONNX Runtime + DirectML**  
   - Works out of the box on all modern GPUs.  
   - Many UIs (e.g., SD.Next) have first‑class ONNX+DirectML modes.  
   - Best baseline for Stable Diffusion on Windows with Radeon.

2. **torch‑directml or DirectML backend in PyTorch**  
   - Integrates DirectML with PyTorch APIs but usually lags behind mainline PyTorch in version support.
   - Useful where ONNX Runtime does not provide enough flexibility.

3. **ZLUDA**  
   - Re‑implements enough of the CUDA stack to let CUDA‑only apps (including some Stable Diffusion UIs and tools) run on AMD GPUs.
   - Actively developed but still evolving; best used as a separate, clearly isolated stack.

4. **ROCm for Windows Preview**  
   - Experimental support for PyTorch ROCm on Windows for select Radeon GPUs and Ryzen AI devices.
   - Not yet a full replacement for Linux+ROCm; recommended mainly for early adopters.

5. **WSL2 + ROCm**  
   - Runs a Linux environment inside Windows with ROCm support.  
   - AMD provides walkthroughs for running ComfyUI with ROCm inside WSL2.  
   - Often the most predictable way to get “Linux‑class ROCm” behavior on a Windows host.

Your own summary of these options emphasizes a **decision tree**:

- If you want stability and performance with full ROCm, prefer **Linux + ROCm** or **WSL2 + ROCm**.
- If you want convenience on Windows, start with **ONNX Runtime + DirectML**; add ZLUDA or ROCm Preview carefully as secondary options.

## 7. Troubleshooting and common pitfalls

### 7.1 ROCm misconfiguration and “bad path” symptoms

Your ROCm “bad path” note distills a common pattern on MI300X and, to a lesser extent, consumer GPUs:

- **Symptom**: Very low GPU utilization (1–2%), extremely low tokens/s or it/s, and high CPU usage.
- **Likely causes**:
  - Missing or misconfigured **FlashAttention** or specialized attention kernels.
  - Using a generic PyTorch build instead of ROCm‑tuned builds.
  - NUMA auto‑balancing enabled on multi‑GPU servers, causing stalls.
  - Insufficient or misconfigured RCCL channels leading to poor inter‑GPU bandwidth.
  - Overly large `max_num_seqs` or other engine settings triggering slow fallback paths.

The fix is to systematically:

1. Use AMD’s **prebuilt ROCm images** for vLLM or TGI.
2. Confirm that logs show the correct attention backend (FlashAttention, CK, or AITER).
3. Disable Linux NUMA auto‑balancing and set recommended RCCL/NCCL environment variables.
4. Reduce and tune batching parameters (`max_num_seqs`, `gpu_memory_utilization`) and confirm KV cache placement.
5. Use ROCm tests (e.g., `rccl-tests`) to validate fabric performance before blaming the LLM engine.

### 7.2 ROCm vs. DirectML expectations

- ROCm is more performant but also more sensitive to version mismatches; successful deployments usually pin OS, kernel, ROCm, PyTorch, and model frameworks tightly.
- DirectML is easier to get running on Windows but typically delivers **lower peak performance** than a tuned ROCm stack on Linux; it is ideal for “good enough” local generation.

### 7.3 PyTorch ROCm quirks

- Seeing `"cuda"` as a device string on AMD is expected; you should check **`torch.version.hip`** to confirm ROCm usage.
- Some libraries (e.g., bitsandbytes, certain Triton kernels) may require ROCm‑specific builds or patches; upstream support is improving but may lag CUDA.

### 7.4 Model and tooling maturity

- Nvidia still has the most extensive and polished ecosystem for advanced AI workloads.  
- AMD’s ecosystem is strongest for **datacenter MI300** (via ROCm + vLLM/TGI/Optimum) and increasingly solid for **Radeon + Stable Diffusion** and **LLM inference/PEFT** on Linux.  
- Video models, advanced reinforcement‑learning fine‑tuning, and some quantization pipelines may still have rough edges on AMD.

## 9. Limitations, caveats, and open questions

1. **Ecosystem maturity** – CUDA still has the broadest tooling, examples, and community support, particularly for cutting‑edge models and research. AMD’s stack is strong but narrower; expect to spend more time aligning versions and following vendor guidance.

2. **ROCm platform constraints** – ROCm officially targets specific GPUs, operating systems, and kernels. Some older or less common AMD GPUs are not supported, leading to confusion among consumers who expect “any Radeon” to work like “any GeForce.”

3. **Quantization and specialized kernels** – Tools like bitsandbytes, Triton‑based attention kernels, and some quantization workflows tend to land on CUDA first and on ROCm later. This can temporarily limit model choice or require manual patches.

4. **Windows vs Linux** – Native ROCm on Windows is still very new; for production or advanced usage, Linux remains the recommended OS for AMD AI workloads. Windows users should lean on DirectML and ONNX Runtime for stability.

5. **Documentation fragmentation** – AMD’s ecosystem involves ROCm docs, PyTorch notes, ONNX Runtime docs, Hugging Face Optimum‑AMD, and community posts. This fragmentation can make it hard to see the full picture without a consolidated KB like this.

6. **Rapid change** – ROCm, Optimum‑AMD, vLLM, ONNX Runtime, and Windows GPU support evolve quickly. Always re‑check official docs for compatibility matrices and installation instructions before making hardware purchases or large upgrades.

# Hugging Face and Retrieval-Augmented Generation (RAG)

## 1. Background and overview

This document summarizes how to build and operate Retrieval-Augmented Generation (RAG) systems around the Hugging Face ecosystem. It combines:

- Official Hugging Face documentation and Open-Source AI Cookbook notebooks on RAG, embeddings, inference, and multimodal retrieval.
- Your existing RAG and Agentic RAG notes and design docs.
- Community blogs, repos, and tutorials focused on better RAG practices.

### 1.1 What RAG is

Retrieval-Augmented Generation (RAG) is an architecture where a language model (LLM) answers questions using both:

1. **Parametric knowledge** inside the model (what it learned during pretraining/fine-tuning).
2. **External knowledge** retrieved at query time from documents, databases, APIs, or tools.

A standard RAG loop:

1. **User query** arrives.
2. System **retrieves** potentially relevant passages from a knowledge base (vector DB, search index, files, logs, code).
3. Retrieved snippets are **inserted into the prompt** (or a structured context) for the LLM.
4. LLM **generates an answer**, ideally grounded in those snippets and accompanied by citations.

RAG is useful when you need domain-specific knowledge, freshness beyond a model’s training cutoff, and traceability (being able to show where an answer came from).

### 1.2 Where Hugging Face fits in a RAG stack

At a high level, Hugging Face provides most of the ingredients you need for a RAG system:

- **Models and data**
  - Open-source LLMs, embedding models, rerankers, and RAG-oriented datasets.
- **Inference infrastructure**
  - **Text Embeddings Inference (TEI)** for high-performance embedding and reranking servers.
  - **Text Generation Inference (TGI)** for serving LLMs with batching, streaming, and multi-GPU support.
  - **Inference Providers** and **HF Inference**, offering OpenAI-compatible chat APIs and hosted inference for many models.
- **Docs and cookbooks**
  - A rich RAG section in the Open-Source AI Cookbook (advanced RAG, evaluation, unstructured-data RAG, Milvus/Elasticsearch/MongoDB RAG, Graph RAG, Agentic and multi-agent RAG, multimodal RAG).
- **Orchestration options**
  - Integrations with LangChain and other frameworks.
  - Native agents via **smolagents** and the **Agents Course**.
  - Tools and servers that plug into the **Model Context Protocol (MCP)**.

The rest of this document explains how these pieces fit together in concrete, implementation-oriented patterns.

## 2. RAG patterns in Hugging Face docs and cookbooks

Hugging Face’s Open-Source AI Cookbook is the primary “source of truth” for RAG patterns on HF. This section summarizes recurring patterns across those cookbooks.

### 2.1 Advanced RAG on Hugging Face docs

The **Advanced RAG** notebook shows an end-to-end RAG system on Hugging Face documentation using LangChain:

- **Corpus**: HTML docs for Hugging Face libraries, crawled and normalized.
- **Chunking**:
  - Split by headings and sections rather than fixed characters.
  - Preserve hierarchy (page → section → heading → paragraph) as metadata.
- **Embeddings**:
  - Use a sentence-embedding model (e.g., GTE, BGE) deployed via TEI or Inference Providers.
- **Indexing**:
  - Store vectors plus metadata in a vector DB.
- **RAG chain**:
  - Query → embed → retrieve top-k chunks → build a prompt with context and citations → call a chat model through HF Inference / Inference Providers.
- **Advanced options**:
  - Query rewriting, reranking, semantic caching, and multi-step retrieval for harder questions.

This notebook is the canonical example of “HF + LangChain + RAG” and is a template for many production systems.

### 2.2 RAG on custom / unstructured data

Another cookbook focuses on RAG over **unstructured data** such as PDFs, Word docs, HTML, emails, and slide decks:

- Use specialized loaders (Unstructured, Docling, etc.) to extract text, headings, tables, and layout.
- Normalize content while preserving structure (e.g., headings, code blocks, table cells).
- Chunk into semantically coherent segments rather than arbitrary fixed-length chunks.
- Embed with a strong general-purpose embedding model served via TEI or local `transformers`.
- Index in a vector store (Chroma, Milvus, Qdrant, Elasticsearch, MongoDB, etc.).
- Build a RAG pipeline similar to the Advanced RAG notebook, but tuned for noisy real-world documents.

This pattern maps cleanly onto document-heavy use cases like technical manuals, NEC/code-checking, policy documents, or log archives.

### 2.3 Vector DB cookbooks (Milvus, Elasticsearch, MongoDB)

Several cookbooks show HF RAG with specific vector DBs:

- **RAG with Hugging Face and Milvus** – integrates TEI with Milvus, demonstrating how to:
  - Deploy TEI for embeddings.
  - Push vectors into Milvus collections.
  - Retrieve and feed results into an LLM via Inference Providers.
- **RAG with Gemma + Elasticsearch / MongoDB** – similar designs but with different storage engines:
  - Index textual fields in Elasticsearch or MongoDB Atlas Search.
  - Use embedding fields alongside keyword fields for hybrid retrieval.
  - Call Gemma or other open LLMs through Inference Providers or TGI.

These notebooks are practical blueprints for choosing a storage layer without changing higher-level HF components.

### 2.4 Knowledge-graph RAG and reasoning

The **RAG with Knowledge Graphs (Neo4j)** cookbook adds a structured layer on top of RAG:

- Build a knowledge graph from documents (entities, relationships, attributes).
- Use embeddings and BM25 for initial recall.
- Use graph queries to walk explicit relationships and gather context.
- Combine graph results with text snippets for grounded answers.

This pattern is especially relevant when you need:

- Multi-hop reasoning.
- Explicit reasoning over relationships, events, or time.
- Auditable, structured representations in addition to vector search.

### 2.5 Multimodal RAG (ColPali + VLMs)

The **Multimodal RAG using document retrieval and VLMs** cookbook demonstrates RAG over visual documents (PDF scans, complex layouts):

- Use **ColPali** (a vision-based retriever) to index document pages as images.
- Use a **vision-language model** (e.g., Qwen2-VL) to reason over retrieved page images plus text.
- Avoid lossy OCR pipelines by letting the retriever and generator operate on images directly.

This pattern is important when:

- Layout and visuals (tables, charts, scans) carry meaning that text-only extraction cannot capture.
- You need cross-modal reasoning (e.g., “What does the third column of this table show?”).

### 2.6 RAG evaluation

The **RAG Evaluation** cookbook focuses on assessing RAG quality:

- Generate synthetic question–answer pairs from your corpus with an LLM.
- Run your RAG pipeline on those questions.
- Use LLM-as-a-judge or specialized metrics (e.g., Ragas or judges) to evaluate correctness, groundedness, and helpfulness.
- Compare RAG variants (different chunking, embedders, rerankers, retrieval strategies) with consistent metrics.

Evaluation is critical when iterating on RAG systems, especially once you introduce more advanced or agentic behavior.

### 2.7 Agentic and multi-agent RAG cookbooks

Two key cookbooks link Hugging Face to **Agentic RAG**:

- **Agentic RAG**:
  - Builds an “agent with a retriever tool” concept.
  - The agent can reformulate queries (HyDE, self-query), call retrieval multiple times, and critique retrieved context before answering.
- **Multi-agent RAG System**:
  - Extends Agentic RAG into a multi-agent setup:
    - A web-search agent.
    - A retrieval agent for internal docs.
    - A coordinator agent that routes questions and assembles final answers.

These notebooks show how retrieval is no longer a fixed pre-step but a **tool inside an agent loop**.

### 2.8 Better RAG blog series

The **Better RAG** blog series provides conceptual best practices:

- Argues that naïve chunking and single-step cosine similarity are insufficient at scale.
- Emphasizes structure-aware ingestion (“the text is your friend”), reproducibility, and evaluation.
- Recommends multi-step retrieval, question decomposition, and careful model selection.

The series complements the cookbooks with higher-level design principles and pitfalls.

## 3. Models and infrastructure for RAG on Hugging Face

RAG quality and cost depend heavily on embedding models, LLMs, and serving infrastructure. Hugging Face offers several layers here.

### 3.1 Text Embeddings Inference (TEI)

**Text Embeddings Inference (TEI)** is a dedicated engine for serving embedding and reranker models:

- Designed for high throughput and low latency.
- Supports many common embedding architectures (BGE, GTE, E5, NV-Embed, etc.).
- Exposes HTTP/gRPC endpoints for `/embed` and `/rerank` calls.
- Integrates with **Inference Endpoints** and can be run in self-hosted or air-gapped environments.

Typical usage:

1. Deploy TEI with a chosen embedding model (e.g., `nvidia/NV-Embed-v2`, `BAAI/bge-m3`, `Snowflake/snowflake-arctic-embed-m-v1.5`).
2. From ingestion jobs:
   - Call TEI’s `/embed` endpoint on each chunk.
   - Store embeddings in your vector DB.
3. At query time:
   - Call TEI to embed the user query.
   - Use a vector DB (Milvus, Qdrant, etc.) to find top-k candidates.

TEI is a core building block for HF-centric RAG stacks because it decouples embedding serving from application logic.

### 3.2 Inference Providers, HF Inference, and TGI

Hugging Face offers several ways to serve LLMs for the “generation” part of RAG:

- **Inference Providers**:
  - A router-based API that exposes many models via OpenAI-compatible chat and embeddings endpoints.
  - Used through `https://router.huggingface.co/v1/...` and the `InferenceClient` in `huggingface_hub`.
  - The recommended way to call serverless HF-backed LLMs in 2025.
- **HF Inference**:
  - The serverless “Inference API (serverless)” renamed and integrated into Inference Providers.
  - A specific provider among many; documented as “HF Inference” in Inference Providers docs.
- **Text Generation Inference (TGI)**:
  - A scalable engine for self-hosted LLMs.
  - Often used behind Inference Endpoints or directly in Kubernetes clusters.
  - Supports batching, streaming, and multi-GPU setups.

A typical RAG deployment might use:

- TEI for embeddings and reranking.
- TGI or Inference Providers for chat-completion.
- A vector DB (Milvus, Qdrant, etc.) for retrieval.

### 3.3 Embedding model selection patterns

From both Hugging Face docs and community benchmarks, a practical embedding model strategy is:

- **Default strong dense model**:
  - Example: `nvidia/NV-Embed-v2` or a top performer on the current MTEB retrieval tasks.
- **Hybrid retrieval**:
  - Example: `BAAI/bge-m3`, which supports dense, sparse, and multi-vector retrieval in one model.
- **Memory-sensitive deployment**:
  - Example: `Snowflake/snowflake-arctic-embed-m-v1.5`, which supports “matryoshka” embeddings (truncate dimensions without retraining).

Guidelines:

- Start with a robust, well-maintained general-purpose embedding model.
- Evaluate on your own dataset (hit@k, answer correctness).
- Only change models or fine-tune if you see clear domain-specific gains.

### 3.4 Rerankers

Rerankers improve precision by rescoring candidate chunks given the query:

- A common choice is `BAAI/bge-reranker-v2-m3`, which works well with BGE and other embedders.
- TEI can serve rerankers via a `/rerank` endpoint.
- A typical pattern:
  - Retrieve top 50–100 candidates via embeddings.
  - Rerank with a cross-encoder and keep the top 5–20 for the LLM.

Reranking often yields larger gains than swapping embedding models, especially for noisy or heterogeneous corpora.

### 3.5 Multimodal retrieval and models

For multimodal RAG, Hugging Face supports:

- **ColPali**:
  - A vision-based retriever that treats document pages as images.
  - Uses a vision-language backbone to encode layout, text, and visuals.
  - Outputs multi-vector embeddings suitable for late-interaction retrieval.
- **Vision-language models (VLMs)** such as **Qwen2-VL**:
  - Accept images plus text.
  - Can answer questions about retrieved page images, charts, tables, and scans.

A multimodal RAG stack looks like:

1. Ingest PDFs as images (one image per page).
2. Use ColPali (or similar) to index these images.
3. At query time, retrieve relevant pages as images.
4. Pass images plus text (e.g., query + retrieved captions) to a VLM like Qwen2-VL for answer synthesis.

## 4. Orchestration frameworks in the Hugging Face ecosystem

RAG needs orchestration around retrieval and generation. Hugging Face supports several approaches.

### 4.1 Hugging Face + LangChain

The **`langchain-huggingface`** partner package is the recommended way to use HF models in LangChain:

- `ChatHuggingFace` – wraps chat-completion models called via Inference Providers.
- `HuggingFaceEndpoint` – wraps text-generation endpoints (HF Inference, Inference Providers, Inference Endpoints).
- `HuggingFaceEmbeddings` / `HuggingFaceInferenceAPIEmbeddings` – embedding interfaces for local models or Inference Providers.

In a typical LangChain RAG stack:

1. Use `HuggingFaceEmbeddings` for indexing docs into a vector store (FAISS, Qdrant, Milvus).
2. Create a retriever from that vector store.
3. Use `ChatHuggingFace` or `HuggingFaceEndpoint` as the LLM for answer generation.
4. Optionally plug in TEI as the backend for embeddings (LangChain has TEI integrations as well).

This keeps HF as the model and inference layer, with LangChain handling chains, tools, and higher-level RAG logic.

### 4.2 smolagents and the Agents Course (Agentic RAG)

**smolagents** is Hugging Face’s agent framework. The official Agents Course and docs show how to build **Agentic RAG** with smolagents:

- Define **tools** by subclassing `Tool` (e.g., a `RetrieverTool` that queries your vector DB or BM25 index).
- Build a `CodeAgent` or `ToolCallingAgent` that can use these tools.
- Implement an Agentic RAG loop where the agent:
  - Reformulates queries before retrieval (HyDE, self-query).
  - Calls the retriever multiple times.
  - Critiques intermediate results before producing a final answer.
- Extend to **multi-agent RAG** with:
  - A web-search agent.
  - A documentation retriever agent.
  - A coordinator agent that routes tasks.

This approach keeps everything within the HF ecosystem (smolagents, TEI/TGI, Inference Providers, HF datasets) and mirrors Agentic RAG research patterns.

### 4.3 Model Context Protocol (MCP) and Hugging Face

Hugging Face is a key participant in the **Model Context Protocol (MCP)**:

- The **Hugging Face MCP Server** exposes Hub resources (models, datasets, Spaces, tools) as MCP tools.
- Agents that speak MCP can treat HF as a tool provider for:
  - Embedding and generation models.
  - Dataset access.
  - Ready-made RAG Spaces or APIs.

For RAG:

- You can expose your own RAG backends (vector DBs, retrieval APIs) as MCP servers.
- You can use HF MCP Server to query models and datasets that configure or power those backends.
- An MCP-aware agent (in LangGraph, smolagents, or other frameworks) can orchestrate RAG as one tool among many.

## 5. Implementation blueprints

This section provides concrete designs for building HF-centric RAG systems, combining the above components.

### 5.1 Baseline Hugging Face–only RAG stack

This blueprint uses only Hugging Face and standard vector DB components.

1. **Ingestion**
   - Parse documents (PDF, HTML, Markdown, CSV, logs) into text with structure-preserving loaders.
   - Normalize and clean content (remove boilerplate, normalize whitespace).
   - Chunk into 400–800-token segments with 10–20% overlap, respecting headings and logical boundaries.

2. **Embeddings and indexing**
   - Deploy TEI with a strong embedding model (e.g., `nvidia/NV-Embed-v2`).
   - For each chunk, call TEI’s `/embed` endpoint and store vectors in a vector DB (Milvus, Qdrant, etc.).
   - Attach metadata: document ID, title, URL, section path, timestamps, language, type (FAQ, log, spec, etc.).

3. **Retrieval**
   - At query time, embed the user’s question using the same TEI model.
   - Use the vector DB to retrieve top-k candidates (e.g., k=40).
   - Optionally rerank results with a TEI-served reranker (e.g., `BAAI/bge-reranker-v2-m3`) and select top 5–10 chunks.

4. **Generation**
   - Use a chat model via Inference Providers or TGI (e.g., Llama, Gemma, Qwen).
   - Build a prompt that clearly separates:
     - System instructions.
     - User question.
     - Retrieved context (with source labels or citations).
   - Ask the model to answer using only the provided context, and to say “I don’t know” when context is insufficient.

5. **Evaluation and monitoring**
   - Use the RAG Evaluation cookbook pattern to generate synthetic QA and compute accuracy with LLM-as-a-judge.
   - Log queries, retrieved docs, and answers for debugging.
   - Track metrics such as hit@k, latency, and answer quality over time.

This baseline stack is enough for many documentation assistants or internal knowledge-bases.

### 5.2 Hugging Face + LangChain RAG stack

To use LangChain for orchestration while keeping HF as the model provider:

1. **Embeddings**
   - Use `HuggingFaceEmbeddings` or TEI embeddings integration for indexing.
   - Prefer TEI when you need high throughput or centralized serving.

2. **Vector store and retriever**
   - Use FAISS, Qdrant, Milvus, or other LangChain-compatible stores with your embeddings.
   - Create a retriever via `.as_retriever(search_kwargs={"k": k})`.

3. **Generation**
   - Wrap the HF chat model with `ChatHuggingFace` (for chat-completion) or `HuggingFaceEndpoint` (for text-generation).
   - Make sure the chosen model is provider-backed for the relevant task (chat vs text generation).

4. **Chain / graph**
   - Build a simple RAG chain:
     - Retrieve → format context → call LLM → return answer + citations.
   - Or build an LCEL graph / LangGraph with:
     - Query rewriting.
     - Multi-step retrieval.
     - Tools (SQL, code, web search).

5. **Agentic extensions**
   - Wrap the retriever as a LangChain tool and construct an agent that can decide when to call it.
   - Use ReAct or plan-and-execute styles to interleave retrieval and reasoning.

This blueprint is appropriate when you are already invested in LangChain or want its vector store and agent ecosystem.

### 5.3 Local/offline RAG with GGUF / ONNX

When you need RAG to run locally or in constrained environments:

1. **LLM side**
   - Use GGUF models from the Hugging Face Hub with llama.cpp, Ollama, or GPT4All.
   - Optionally use ONNX-exported LLMs via Optimum ONNX + ONNX Runtime.

2. **Embedding side**
   - Use lightweight embedding models exported to ONNX (via Optimum) or run them via TEI in a local container.
   - For pure on-device use (desktop apps), consider Transformers.js + ONNX Runtime Web.

3. **Pipeline**
   - RAG pipeline is similar: local embedding → local vector DB → local LLM.
   - HF still provides models and export tools; you provide runtime and orchestration.

This blueprint is useful for privacy-sensitive use cases, offline tools, and personal knowledge assistants.

## 6. Limitations, caveats, and migration notes

Even with a strong HF-based stack, there are important caveats to keep in mind.

### 6.1 Embedding and chunking limits

- Fixed-size embeddings cannot capture every nuance of long documents.
- Chunk size introduces a trade-off:
  - Smaller chunks → better recall but more noise and storage.
  - Larger chunks → better local coherence but risk including irrelevant text.
- Hybrid dense + sparse retrieval and rerankers can mitigate some limitations but not all.

### 6.2 Domain shift and multilinguality

- Embedding models trained on web data may underperform on specialized jargon (legal, medical, code).
- Multilingual performance varies; tests on your actual language mix are essential.
- Fine-tuning or adapter-based approaches may be needed for high-stakes domains.

### 6.3 Latency, cost, and complexity

- Advanced RAG techniques (multiple retrieval rounds, rerankers, agentic loops, multimodal retrieval) increase latency and cost.
- Semantic caches and response caches help but add system complexity.
- TEI and TGI help scale efficiently, but architecture and ops practices still matter (autoscaling, observability, rate limiting).

### 6.4 Migration from legacy HF APIs

- The legacy `api-inference.huggingface.co` endpoint has been superseded by **Inference Providers** and the router:
  - Applications must update base URLs, tokens, and sometimes request formats.
  - Only provider-backed models work with certain tasks (e.g., chat-completion).
- Older LangChain integrations (e.g., community `HuggingFaceHub` LLM) may be deprecated or lack new features.
- When upgrading:
  - Verify which models are provider-backed for chat/embeddings.
  - Pin compatible versions of `huggingface_hub`, `langchain`, and `langchain-huggingface`.
  - Add smoke tests around common RAG flows.

### 6.5 Evaluation and reproducibility

- LLM-as-a-judge methods can be biased or unstable; it is useful to track several metrics (faithfulness, relevance, fluency) and use multiple evaluation prompts or judges.
- RAG experiments should be logged with:
  - Exact model versions and providers.
  - Embedding model and index build date.
  - Chunking configuration.
- The Better RAG series and RAG evaluation cookbooks stress reproducibility as a first-class goal.
